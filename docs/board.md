# Board, milestones and setup

Part of the thread documentation: [index](README.md).

The board page and its views, milestones, custom stages, chat-only mode and `/thread:setup`. The page is served on `127.0.0.1` only; see [Security](security.md).

## The board

`/thread:board` opens the board in your browser, on this project's Summary, and prints the address `http://127.0.0.1:47800/#/<project>`. The address has no token, and Claude is not shown the access token in a tool result (an agent with a shell can still read `board.token` or `board-link.txt` from the data directory; see [security](security.md#security)). The browser is opened with a one-time code (`?c=<code>`), not the token: a link's arguments can be read from the process list while the browser starts, so the token is kept off the command line. The page trades the code for the token with one request (the code works once and for 2 minutes, and is gone from the address bar at once), and keeps the token in the browser's local storage (and in the tab's session storage, which a board served by an older plugin version reads), so the address (and a card's address such as `#/<project>/c37`, which is what the chat links to) opens in any tab of that browser afterwards. A token or code that arrives in the address always replaces a stored one. The link with the token (`?t=<token>`) is saved in `board-link.txt` in the [data directory](configuration.md#configuration) (owner-only; the answer names the file whether or not a browser opened), for opening by hand. Stopping the board (`--stop`) replaces the token, so a browser that kept the old one opens nothing from then on (run `/thread:board` again). In a browser that has never opened the board, the address shows "The board needs its access link"; run `/thread:board` again. If you only want the address, ask Claude for it: it calls `board_open` with `open: false`, which opens nothing.

- **From your phone:** `/thread:board --tunnel` opens a remote link through a Cloudflare tunnel (a **Phone link** item with a Copy button appears in the top bar of the board on this computer while it is open); the remote page has a **Remote** badge and fewer controls; see [Opening the board from your phone](security.md#opening-the-board-from-your-phone-tunnel).
- **One board, served by one session.** The first Claude Code session to start serves the page and the others share it. When a session on a newer plugin version starts, or runs `/thread:board`, it replaces a board served by an older version; a session that is already running does the same within a few seconds. So after an update you reload one session's window, then the browser tab. Sessions that were open before the update keep running the old plugin code until their window is reloaded: until then they ignore newer settings such as your own stages or chat-only mode. A board from before 0.8.2 cannot be replaced this way (see [Troubleshooting](troubleshooting.md#troubleshooting)). `/thread:board --stop` stops the page for every session until someone runs `/thread:board` again; cards and threads are not touched.
- **Plugin version:** the header shows the version that served the page. If the server changes to a different version while the tab stays open, a note under the toolbar says so. When the board is now served by a newer version, the note shows both versions and a **Reload** button to load the current page. When it is served by an older version (a session that has not been updated took over), the note says so and tells you to run `/thread:board` in an updated session and then reload the page; there is no Reload button, since reloading would only show the older page. The note gives way to the older-session note (about missing stages and milestones) when that one is showing.
- **Update notes:** after the plugin was updated, a note under the header says **Updated to X.Y.Z (from A.B.C)**; **What's new** opens that release's entry from the plugin's own `CHANGELOG.md` (or "See the release notes" and the address of the releases on GitHub when it has no entry). With the [update check](configuration.md#staying-up-to-date) on, a second note says **thread X.Y.Z is out** and shows the two update commands with **Copy** buttons. **Dismiss** puts a note away for that version, in this browser only. The remote (tunnel) page shows neither. The board makes no network call for them: the server reads the changelog and the record of the check from disk.

### Projects home and top bar

One page serves every project.

![The projects home: three project tiles, acme-shop with 20 open, 13 done, 6 waiting in red and 1 running, acme-admin and acme-docs with nothing waiting](home.png)

- **Projects home.** The address without a project (`#/`) opens a home with one tile per project: its name and folder, how many cards are open and done (milestones are not counted; a chat-only project counts its threads), how many items [wait for you](reviews-and-waking.md#waiting-for-you) (in red when there are some), how many threads are running, and when it was last active. The tiles are in order of last activity when the page loads and do not move while you look at them. Click a tile to open the project. A tile says **folder missing** when the project's folder was deleted, and **chat-only** for a [chat-only](#chat-only-mode) project once you have opened it on this page.
- **Switching.** Inside a project, the header has an **All projects** link back to the home and a select to move to another project, which opens on its Summary. The select shows `name · 2 waiting` for a project with items waiting for you, `(folder missing)` for one whose folder is gone, and the parent folder's name when two projects share a name.
- **Top bar.** A project has five views: **Summary**, **Board**, **List**, **Milestones** and **Waiting**, the last with a red count while something waits for you. A project opens on its Summary. A chat-only project has **Board** only. Waiting is the Board with only the cards that have items waiting for you; while something waits, `w` goes there from the Summary, the List and the Milestones, and back to the Board from Waiting. The search box works on the Board, Waiting and the List. **New card** and `n` work in every view. A card's page opens over the view you came from, and **Back** (or `Esc`) returns to it.
- **Addresses.** Every place has its own address, so Back, Forward and bookmarks work. `#/` is the projects home. `#/<project>` is a project's first view (Summary; Board for a chat-only project). `#/<project>/summary`, `/board`, `/list`, `/milestones` and `/waiting` are the views. `#/<project>/<card id>` is a card's page, and `#/<project>/new` is the new-card form. The old `#<card id>` form still works and opens the card in the selected project. An address for a project the board does not know opens the project of the session that serves the board.
- **A missing folder.** A project whose folder was deleted is shown read-only and can be forgotten, which removes its saved cards and logs. The bar above its view says so and has the button.

### The Summary view

A project opens on its Summary, a page of work analytics (a chat-only project has the Board only). It is worked out in your browser from the cards the page already has. Milestones are not counted as work.

![The Summary of acme-shop: the filter bar (last 8 weeks, all milestones, workers, types, priorities and labels); 27 open, 11 in progress, 5 done in the last 7 days, 6 open bugs and 2 waiting; a line chart of cards created, done and open at the end of each week over 8 weeks; work by worker with done counts and tokens; the oldest waiting items; the milestones with their progress; the time in a stage; and the About these numbers panel](summary.png)

- **Five tiles.** The open cards (not in the Done stage or a later one), the cards in the working stage (the tile takes that stage's name, In progress by default), the cards completed in the last 7 days (a card's completion date is the last time it moved into Done or a later stage from an earlier one; a move from Done to Released does not change it, and reopening a card and finishing it again gives it a new date), the open bugs, and the items waiting for you. The waiting tile opens the Waiting view when something waits.
- **Filters.** A bar under the heading, styled like the Board's and the List's: **Time range** (Last 7 days, or Last 4, 8, 12 or 26 weeks; 8 weeks by default), **Milestone** (All, each milestone, No milestone), **Worker**, **Type** (Task, Bug, Idea and Thread, each offered only when a card of that type exists), **Priority** and **Label**. A select appears only when the project has something to choose between, and turns accent-coloured while it is set. A worker is named as in Work by worker: from a card's workers, its sub-agent runs and its thread. The filters apply to every number on the page: the tiles, the chart, Work by worker, Waiting for you, Time in a stage and the milestones (a milestone filter lists that milestone only; another filter lists only the milestones that have a card it lets through, with their own progress). Two things stay as they are: the Done tile always counts the last 7 days, and the time range sets only the weeks (or days) of the chart. While a card filter is set the bar says how many cards match ("12 of 40 cards"), and **Clear filters** (which hands the focus to the first select) appears while any filter, the range included, is set. A value that nothing offers any more, such as a deleted milestone, is dropped for good rather than returning later. With a worker set, Work by worker lists that worker only. The filters are kept for each project while the browser tab is open, and survive the page refreshing itself. They are separate from the Board's and the List's.
- **Created, done and open by week.** A line chart for the chosen weeks, counted on each card's completion date. Weeks start on Monday, in your browser's time zone. With **Last 7 days** it has one point per calendar day instead (midnight to midnight, today last): the axis names each day (`Thu 8`, today as `Today`), the title and subtitle say days, the Open line is the cards open at the end of each day (today's point reads "Open now"), and the tooltip and table give the date (`Tue, Oct 14`). The tiles stay as they are. The choice is stored as `7d`; a page of an older version that reads it falls back to 8 weeks. Two lines share the upper plot: **Created** (solid line, hollow circles) and **Done** (solid line, filled diamonds). The **Open** line (dashed, triangles) is how many cards were still open when each week ended, counting cards from before the chart too; it has its own, shorter plot below with its own axis, because a backlog is usually many times a week's flow and one shared axis would flatten the two lines you care about. A card that was done and then reopened counts as open for its whole life; a card with no creation time is not counted, so the line can be a little lower than the Open tile. Point at a week, or focus the chart (Tab) and use the Left and Right arrow keys (Home and End jump to the first and last week, Esc closes it), to see a small tooltip with that week's dates and its three numbers (the current week's open count reads "Open now"), a guide line and marked points; the tooltip stays inside the chart, and a touch on the chart does the same until you touch elsewhere or swipe. A screen reader hears the week only when you move with the keyboard. A redraw for new data keeps the week and the focus where they were. The week labels thin out when there are many weeks. Each line has its own colour, line style and marker, so none depends on colour alone, and the legend shows them. **Show as table** lists the same numbers; the chart has a text summary for screen readers. It works in the light and dark themes and in forced-colours mode, and has no animation.
- **Work by worker.** For each worker, the number of done cards it worked on and the tokens it used, with up to 8 rows and "and N more". The done count comes from the [workers](#card-fields-workers-and-the-done-gate) listed on each done card. The tokens come from sub-agent runs on cards and from thread turns, and not from the main session. A task a thread worked on lists the thread's lane (`lane:code-codex`) or agent (`agent:reviewer`) as a worker and counts as done for it; a thread with neither is `thread:c9`. The tokens of that thread's turns are counted once, from the thread card, under that same name (one row for the job), never again from the run on the task. Tokens of a thread that does no card's work and runs with no agent or lane are listed under `thread`.
- **Waiting for you.** The oldest open items, up to 8, each with its kind, card and age; click one to open its card at the Waiting for you section.
- **Milestones.** Up to 6 milestones in number order (M0, M1 … M10, as in the Milestones view; a title with no number comes after the numbered ones), with their state (Open, Empty or Done) and progress bars, each linking to its page, and "and N more" linking to the Milestones view.
- **Time in a stage.** The median time a card stayed in each stage (except the Done stage and the stages after it) before it was moved on, and how many moves that is based on.

A panel at the bottom, **About these numbers**, says what the figures cannot know (and what the filters and the Open line count): a card keeps the last 50 entries of its history, so an older card may show only when it was created and a move that fell out of the history is not counted; a card counts as done on the day it last moved into the Done stage or a later one from an earlier stage (for a thread, when its last turn ended), or on the day it was last updated when that move is not in the history; and work by the main session shows only where Claude recorded a worker. A project with no cards shows zeros and a link to the Board.

### The Board view

The Board shows the cards in columns. The Waiting view is the same page with only the cards that have items waiting for you.

![The Board of acme-shop in six columns from Idea to Done, with bug icons, priority arrows, label chips, milestone tags, blocked, criteria and waiting marks on the cards, and a finished thread in Review](board.png)

The same page in the dark theme, which the button in the header switches to:

![The Board in the dark theme](board-dark.png)

- **Columns follow your stages.** There is one column per stage, in order, labelled with the stage labels. With the defaults there are six; with [custom stages](#custom-stages) there are 2 to 10. In [chat-only mode](#chat-only-mode) there are three fixed columns instead: New, Review and Done.
- **Cards** show their id, kind (task, idea, milestone or thread) and title. A card under a milestone shows a tag with the milestone's title; click it to filter the board to that milestone. A milestone is not drawn on the Board: it has no stage, so it has no column (the columns and their counts leave milestones out). A task or idea with a [delegation lane](delegation.md#delegation-lanes) shows a lane tag (`code-codex · codex`) in its foot. Thread cards also show their state, the number of turns, the session that started them, a **Not reported** tag when they hold a result the main session has not pulled, the tokens they have used, and their agent when they run as one.
- **Working now.** Being in a stage such as In progress does not mean anything is running, so a card shows it when something is. First in the card's foot, a small pulsing dot with a short text: the agent type of a running [sub-agent run](#task-and-idea-pages) (`worker working`), `3 agents working` when several run, and on a thread its Running pill (`Running`, or `Running on code-codex` for a [lane](delegation.md#delegation-lanes) thread). A task that a thread is working on (see [Work of a thread on a card](#task-and-idea-pages)) shows the lane's name too: `code-codex working`. Point at it for the details: each agent type and how long it has been running, or the lane. A run that has had no activity for 10 minutes is shown as `worker quiet` instead, muted and with a dashed ring in place of the dot, because a run whose stop was never recorded (its session ended or crashed) would otherwise look like live work; open the card and use **Mark as stopped** to close it. The same indicator is in the card's screen-reader name (`working now: worker`), in the List (under the title), as a dot beside each open card in the [Milestones view](#the-milestones-view), and in the header of the card's page next to its stage. It appears and goes away as runs start and stop, without reloading the page. With reduced motion turned on in your system the dot does not pulse but is still there.
- **Card fields on a face.** A task, idea or thread shows its [fields](#card-fields-workers-and-the-done-gate) when it has them, and a card without them looks as it always did. A bug has a bug icon beside the kind. A priority mark sits at the right of the top line: two red arrows pointing up for high, two quiet arrows pointing down for low, nothing for normal. Up to three label chips follow the title, with `+2` for the rest (hover for all of them). The foot can carry a red **blocked** tag while any blocker is not yet in the Done stage or a later one (hover for the blockers and their stages), a quiet `3 criteria` tag, a red **not verified** tag on a card in the Done stage or a later one that nobody approved, and a **Full access** tag (a diamond icon) on a card you allowed [full access](#full-access) on or a thread that runs with it.
- **Waiting for you:** a red pill in the toolbar, the Waiting view with a red count in the top bar, a tag on each card that has open items and a section on the card's page; see [Waiting for you](reviews-and-waking.md#waiting-for-you).
- **Gear menu:** every card with an action has a small gear that opens a menu of its actions, so you do not have to open the card first. Each action does what the same action does on the card's page, with the same confirmation step.
  - A card with open [waiting items](reviews-and-waking.md#waiting-for-you) starts its menu with **Answer waiting items (N)**, which opens the card's page at that section.
  - A **thread**: **End thread**, **Report to main session** (or **Cancel queued report**), **Delete**. End thread is not offered once the thread has ended and its confirmation names the stage the card moves to (the one with the done role); Report only while the main session has not pulled the result; Delete is greyed out while a turn is running.
  - A **task or idea**: **Notify Claude…** (only while the card is new from you or new in the repo, see [Notify Claude](#notify-claude); **Notify Claude again…** once a request is open), **Move to** each stage (the current one is marked and cannot be chosen), **Set milestone** (each milestone, or No milestone; shown once a milestone exists), **Start as thread** (greyed out, with the reason as its hover text, when the card has acceptance criteria or a Blocked by list) and **Delete**. Start as thread opens the card's page at the start step, where you choose the session, worker, Brief or Full copy and access; Notify Claude opens it at the notify step.
  - A card with nothing to offer has no gear: on a project whose folder is missing (read-only) no card has one. A milestone is not on the Board, so it has none; its own page has **Copy report** and **Delete**.
  - With the keyboard, Tab to the gear and press Enter or Space (holding the key does not choose anything); the arrow keys, Home and End move through the menu, which scrolls to the focused item when it is long, Enter chooses, Esc closes it and returns to the gear, and Tab closes it. Clicking elsewhere closes it too. The gear never starts a drag or opens the card.
- **Toolbar, in two rows.** The first row has the search (id, title or note), the **Session** select (the session that started the threads; "All sessions" first), the **Milestone** select (shown once a milestone exists; "All milestones", each milestone by title, or No milestone) and, at the right, **New card**. The selects have no label of their own: the first option names the filter, and a select that is not on it turns accent-coloured so it is plain that a filter is on. The second row has the toggle chips, **Threads only** and **Waiting for you** (the red chip; only while something waits), which fill with colour while they are on; then, while the waiting filter or the Waiting view is on, the small key of the waiting kinds; and, at the right, how many cards are left ("3 of 33 cards") with a **Clear filters** link while a filter is on. On a narrow window the search shares the first row with New card and the selects follow, two to a line. The search, session and milestone filters are shared by the Board, Waiting and the List. A button in the header switches between light and dark.
- **Task and idea cards** open in the same three-pane workspace as a thread (see [Task and idea pages](#task-and-idea-pages) below). **Milestone cards** (opened from the Milestones view, the List or the Summary) open as a full page where you edit the title and note, with the milestone's state beside its progress and a list of its cards, grouped by stage, each row a link to that card, and **Copy report**. A milestone page has no Status. Drag a card to another column to move it to that stage. In the new-card form, **Type** is Task, Bug, Idea or Milestone (a bug is a task with the type bug), and a task, bug or idea can be given a milestone, a priority and labels. When Type is Milestone the form hides Status and Milestone: a milestone has no stage and cannot be in another milestone.
- **Start as thread** turns a task or idea card into a thread (a milestone cannot be). You choose the session it reports to, **Brief** or **Full copy**, read-only or able to edit files, and a [Worker](delegation.md#choosing-a-worker-on-the-board) (Claude (default), a sub-agent from your `.claude/agents/`, or a delegation lane). With Brief, the title is the task and the note is the brief, since nobody writes one on the board. With Full copy, the title and note are the task. For a card that has **Allow full access** on, the Mode choice has a third option, **Full access** (no sandbox, no permission checks); the server checks the card again when you press Start. See [Full access](#full-access).
- **Thread cards** open full-window:
  - **Centre:** the conversation, and a box to send a follow-up. A running turn shows its steps as they happen. A finished turn folds them into one line with its duration and tokens, such as "6 steps · 3m 00s · 48k tokens".
  - **Left:** the thread's session id, the session that started it, a `claude --resume <id>` command that opens the thread as a normal conversation in a terminal, its context (Brief or Full copy), its agent or model and effort (a lane thread: the lane's provider, model, effort or variant, access, source and whether a follow-up is possible, and the provider's session id in place of a `claude --resume` command), its milestone (changed with a select that saves at once), the tokens used, the brief it was given, the latest digest, and every decision across turns. The report command has a copy button. **Report to main session** queues the report: it is delivered with your next message in the session that started the thread, and repeated until that session makes it.
  - **Right:** the trace, a timeline of what the thread did, labelled Did, Found, Decided, Changed and Open, with file references. Clicking a step scrolls the conversation to that turn. For a lane thread it opens with one line about what its provider shows (see [Delegation lanes](delegation.md#delegation-lanes)).
- **Keys:** `/` focuses search, `n` adds a card, `w` shows or hides only the cards that wait for you (on the other views it goes to Waiting, and from Waiting back to the Board), `Esc` closes a panel.

### The List view

**List** shows every card of the project as a table, threads and milestones included. A chat-only project has no List.

![The List of acme-shop filtered to the milestone Launch v1 and sorted by priority: a table with ID, Type, Title, Stage, Priority, Labels, Milestone, Worked by, Waiting and Updated, with blocked and done, not verified tags under some titles](list.png)

| Column | Shows |
|---|---|
| ID | The card id. |
| Type | Task, Bug, Idea, Thread or Milestone. |
| Title | The title. A card with a blocker that is not done yet shows `blocked by c4` under it (only the open blockers are named), and a card in Done or a later stage that nobody approved shows `done, not verified`. |
| Stage | The stage's label. A milestone has no stage, so it shows its state and progress instead, such as `Open · 5/14` or `Done · 3/3` (`Empty` with no counted card). Sorting by Stage puts the milestones after every stage: open, then empty, then done. |
| Priority | High, Normal or Low. |
| Labels | The first two, with `+N` for the rest. |
| Milestone | The title of the milestone the card is under. |
| Worked by | The last worker the card lists, with `+N` for the others. |
| Waiting | The number of items waiting for you, in red. |
| Updated | When the card last changed. |

- **Sorting.** Click a column header to sort by it, and click it again to reverse. The table starts sorted by Updated, newest first. Priority and Waiting start with the most important first, and Stage follows the order of your board columns. A card with nothing in the sorted column goes last, whichever way you sort. Each project keeps its own sort and filters while the page is open.
- **Filtering.** The search box (id, title or note) and the Session and Milestone selects work as on the Board. **Type**, **Priority** and **Label** selects ("All types", "All priorities", "All labels" first) sit in the first row after them and offer only values some card has, and appear when there is something to choose between. **Blocked** and **Done, not verified** are toggle chips in the second row. **Blocked** shows the cards that have at least one blocker not yet in the Done stage or a later one (the **Blocked by** field; a card whose blockers are all finished is not blocked, as on the board), the **Bug** type shows every card whose type field is `bug`, an idea or a thread included, and **Done, not verified** shows the cards in the Done stage or a later one with acceptance criteria that nobody approved. The right end of the second row says how many cards match ("6 of 36 cards"), with **Clear filters**. The Threads only button is not shown, because Type does that job.
- **Opening a card.** Click a row, or focus it and press Enter or Space, to open the card's page. `Esc` or the browser's Back button returns to the List.
- **Narrow windows.** The Labels, Milestone and Worked by columns are hidden, and Updated too on a very narrow one; if the rest still does not fit, the table scrolls inside its own box.

### The Milestones view

![The Milestones map of acme-shop: M0 to M5 as rings joined by lines that show which milestone depends on which, M2 picked with what it depends on and what is left before it](milestones.png)

**Milestones** lists the milestones in number order: by title with numbers compared as numbers (`M0`, `M1`, `M2` … `M10`, also `1. Setup` or `v2.1`), whatever their state, so a done milestone keeps its place; a title with no number comes after the numbered ones. A line at the top says how many are done, which milestones are open **now** (open, with every milestone they depend on done; "2 open, none ready" when open ones only wait on each other), how many items wait for you, and how many dependencies the cards make. **Map** and **Cards** above it switch between two ways to see them.

**Map** (the default) draws the project as a route from left to right:

- **A ring per milestone**, with its number inside (`M3`; a title with no number, such as "Holiday sale", gets a plain dot and is called by its title, cut to 24 characters; two milestones with the same name are told apart by their card id, such as "M1 (c4)"), its title, its progress (`3/7`) and a shape for its state: a filled circle for Done, a ring for Open, a dashed ring for Empty. The ring fills as cards are done. A milestone you can work on now has the label **Now**; one that still waits on others says **After M2, M3**. A red count with one small icon per kind shows the items waiting for you on its cards.
- **Dependencies come from the cards, and from links you draw.** A milestone has no Blocked by of its own. Milestone A depends on milestone B when a card in A is blocked by a card in B (in the card's **Blocked by**), or when you linked A to B by hand (see **Link milestones by hand** below). Ideas do not count, and a link between two cards of one milestone is not a dependency. Each dependency is a line with an arrow to the milestone that waits, and a number on it: how many card links make it. A line from a done milestone is green. Where the map places them (a milestone you moved stays where you put it), each stands in a column after every milestone it depends on, and milestones with no link at all are in a row of their own, "Not linked to another milestone". If milestones wait on each other (A on B and B on A, or through others: a cycle), the map still draws every milestone, puts the ones in the cycle side by side in number order and draws only the lines between them dashed and in red; a line that only leads into or out of a cycle is drawn as usual, and the top line says "2 open, none ready" when nothing else can start; the picked milestone says it in words too ("Cycle: M9 and M10 depend on each other"). Lines never cross a milestone: one that does not run straight to its neighbour on the same row goes through the gaps between the columns and the rows, each in its own lane, and its number sits on it clear of the milestones and of other numbers.
- **When no card links two milestones**, the milestones stand on one line in number order joined by a dotted line, and the key under the map says it is the number order only, not a dependency.
- **Pick a milestone** with a click, or move through them in number order with the arrow keys (Home and End go to the first and last). The milestone open now is picked when you arrive. The lines to it from every milestone it depends on, directly or through others, are drawn thicker (the walk stops at a done milestone, as "now" does) in the accent colour and those milestones get a dashed outline, so you see the way there. Under the map, the picked milestone shows **Depends on** (each with its number of card links, and "done" when it is), **Needed by**, how far it is ("To reach it: M1, M2 still to finish first; 9 open cards in all, its own included"), **Which cards link it** (each pair of cards, each a link to its page), then its block as in Cards. A button with a milestone's name picks it. The pick, the Map or Cards choice and which "Which cards link it" lists are open are remembered for each project while the page is open, and the block under the map is a polite live region, so a screen reader hears it change.
- **Arrange the map.** Drag a milestone to another cell of the grid: a dashed outline shows where it lands; **Escape** cancels, and a taken cell **swaps**. The layout is saved **on this computer**, per project, in the plugin's data folder (`milestone-layout.json`): never in the repo (other devices have their own) and never in the browser. A milestone you never moved stays where the map puts it. **Reset layout**, next to Map and Cards, asks first, and the layout survives turning on [keeping the board in the repo](storage-and-sync.md#keeping-the-board-in-your-repo-claudethread). On a touch screen press and hold, then drag.
- **Link milestones by hand.** Drag the dot beside a milestone's ring (on hover, and on the picked one) onto another milestone: **that one now depends on this one**, and the arrow points at it. A refusal is said under the map: itself, a link drawn twice, or a **loop of drawn links** (named; a loop made by cards is allowed and drawn as a cycle). A drawn link is a **dotted line** marked "hand", or "2 + hand" when cards link the same two. It counts wherever the map counts dependencies (**Now**, **After**, the route, "To reach it", `board_list`) and **only there: it never holds up a card, a thread start or the done gate.** It is stored on the milestone card as `dependsOn` (at most 20 ids), so in a project [kept in the repo](storage-and-sync.md#keeping-the-board-in-your-repo-claudethread) other devices see it; older versions keep it. A git merge of two clones can make a loop of drawn links: the map draws a cycle and nothing is blocked; remove one link.
- **Name or remove any line.** Every line is a button: hover shows it, and a click, **Enter** or **Delete** (Tab to a line, the arrow keys move along them, or use the **Line** button in the details) opens a small box on it with where it comes from; a press elsewhere or **Escape** closes it. **Rename** takes up to 40 characters (**Enter** saves, **Escape** goes back), shown on the line in place of "hand", cut to about 22 characters with the number of card links after it, and kept on the waiting milestone's card as `linkNames` (shared in the repo; older versions keep it). **Remove link** removes a drawn link. **Remove card links…** lists what will change ("c12 "Checkout" will no longer be blocked by c9 "Cart"") and, after you confirm (the step starts on **Back**), takes exactly those blockers off the cards as they are now, in one update that is the normal card edit (history, the repo and the other rules apply); a link that has changed meanwhile is skipped and said. A line that both make offers both. A name goes with its line: it is dropped when an edit ends the line (a link or blocker taken off, a card moved or removed), except while a card file cannot be read.
- **Without the pointer.** With a milestone picked, **M** moves it: arrow keys move a dashed outline, **Enter** drops, **Escape** cancels. The details have buttons for the same, usable on touch (**Move**, arrows, **Drop here**, **Cancel**), **Add dependency** and **Remove**. A polite line under the map says what happened.
- **Through the tunnel the map is only looked at**: it shows the layout, links and names, and every control that changes them is hidden and refused by the server.
- The map scrolls sideways inside its own box on a narrow window, never the page (dragging works inside it, and it scrolls when you drag near its edge), and is scaled down to the page's width when printed. Each ring is a button whose name says it all in words (title, state, progress, waiting, depends on, needed by), and the lines are only drawing, so a screen reader gets the same facts. It works in light and dark, in high-contrast (forced colours) mode, and with reduced motion.

**Cards** shows each milestone as a block: its title (a link to its page) with a state tag (**Open**, **Empty** or **Done**), a progress bar, a tag with the items waiting for you on its cards (to look at; answer them on the card), "Depends on: M1, M2" when cards link milestones, the number of its cards to do, in progress and done, and up to five of its open cards, each linking to its page. Ideas are left out of every count and of the open cards. In progress counts the cards in the working and review stages, to do counts every other stage that is not finished, and done counts the stage with the done role and any stage after it. When there are more open cards, "and N more" opens the List filtered to that milestone. A milestone whose cards are all done says so. See [Milestones](#milestones) for what a milestone is.

### Task and idea pages

A task or idea card opens the same way a thread does, so you can see what is happening in the task, what an agent is doing, and trace it.

- **Left, "Card":** the editable title, note, status, milestone, [worker](delegation.md#choosing-a-worker-on-the-board) (a lane or a sub-agent) and [card fields](#card-fields-workers-and-the-done-gate) (type, priority, labels, blocked by, acceptance criteria), with **Save**, **Cancel**, **Notify Claude** (while the card is new from you or new in the repo), **Start as thread** and **Delete** pinned under them. Under the fields is a details list: kind, who added the card, when it was created and updated, and **Worked by** (a card with a lane also lists the lane's provider, model, effort, access and source, read-only). Below the form: a summary of the card's agent runs (agent type, running or finished, tokens, when; click one to jump to it) and the card's **History**.
- **Centre, "Agent runs":** each sub-agent run on the card as a turn: the prompt the main session gave it, its steps live while it runs, then the agent's final report. A finished run folds its steps into one line, such as "4 steps · 12s · 27.4k tokens". A card no agent has worked on says so in one line and how to get one. There is **no message box**: only the main session can talk to a sub-agent. **Start as thread** is how you get an agent you can message. A run can also be a turn of a thread that does the card's work (see **Work of a thread on a card** below), shown the same way.
- **Right, "Trace":** one block per run with a step for each tool call (Read, Ran, Edited, Searched, Fetched), clipped to one line each; a call that failed is marked. Clicking a step scrolls to its run.
- **History:** a vertical timeline, newest first, with a rail down the left and one marker per event. The marker's shape and colour say the kind of event (created, moved, moved into the done stage or a later one, edited, a worker noted, or an item [waiting for you](reviews-and-waking.md#waiting-for-you) raised: a question, a choice, a to-do or a review each has its own shape), so it never relies on colour alone. Each entry reads "You moved it" or "Claude edited the title, note": a move shows the two stages as chips with an arrow ("In progress → Needs owner", the names are your stages), the worker Claude named (`agent:worker`, `lane:code-codex`, `thread:c4`, `main`) is a small muted chip, and the time is on the right, relative ("2 d ago") with the exact date and time when you hover it. When the history spans more than one day the entries are grouped under **Today**, **Yesterday** or the date. It shows the newest 8 events; a card with more has a **Show all N events** button (and **Show fewer** to fold it again). It keeps the last 50 entries. It records changes made through the board or Claude's tools; a card made before this feature has only its creation, and a session still running an older plugin version does not add to it. The card's [runs](#task-and-idea-pages) (a sub-agent, or a thread on a lane or not doing the card's work) are drawn in it too, in time order: "Claude started run 2" with the run's worker as the chip (`lane:think`, `agent:worker`, `thread:c5`), then "finished run 2" when it ended well, "run 2 ended" when a thread's turn is over without a recorded success, or "run 2 stopped" otherwise. A run of a thread is always shown as `thread:<card>` (or its `lane:<name>`), never as a sub-agent. At most the newest 10 runs are drawn (each with its start and end), so a long run list does not crowd out the moves and edits. They come from the card's runs on this machine, not from the stored history, so they are kept as long as the run is (a card keeps its newest runs).
- On a narrow window the three panes become tabs (Agent runs, Card, Trace); a card with no run opens on Card.
- **Long text.** The text of a waiting item, a run's prompt, a thread's messages and the brief given to a thread are shown with Markdown structure (paragraphs, lists, code, bold) and the line breaks the writer used; steps run together in one paragraph ("1) … 2) … 3) …") are split into a numbered list. **Tables** (GitHub style, with a header and a `|---|---|` line) are drawn as tables that scroll sideways on a narrow window, and **links** show only their text: a link to an `http(s)` address opens in a new tab (so does a bare `http://` or `https://` address written in the text, shown as the address itself and wrapping when it is long, without the full stop or comma after it; other kinds of address stay text), and any other target, such as a file path with a line number, is shown as a dotted-underlined reference with the target in its tooltip, so a long path never fills the line. Long paths and ids wrap. Headings are in the accent colour, larger for `#`/`##`; a heading or a bold line named like a section is coloured to match the trace chips (Decided, Changed, Open or Next steps, Found or Findings, Risks or Not tested in red, Summary or Result or Done in green). The note of a card or milestone is shown the same way, in a reading frame of its own: a header with the label **Note** and the **Edit** button on the right, then the text in a larger size with roomier lines, headings in their section colour with a hairline under them, bold leads such as `**On return:**` in the accent colour, spaced lists and boxed `code` (Save and Cancel work as before; a new card or an empty note opens in the text box). See [Card and waiting item links](#card-and-waiting-item-links) for ids in the text. **Code blocks.** A fenced block (three backticks or `~~~`, optionally with a language such as `bash`) and a line that is only one command in backticks (such as `npm run build`) are drawn as a code block with a **Copy** icon button at its right: one click copies exactly the text of the block (nothing is added to it) and the button shows a check and **Copied** for a moment; if the browser does not allow copying, the text is selected and the button says to press Ctrl/⌘+C. The language is shown as a small label; a `bash`, `sh`, `shell` or `zsh` block, and a line that is only a command (it starts with a command word such as `npm` or `git`, or with `./`), has a `$` before it that is not copied. A line that is only code with a space in it, such as `` `SELECT * FROM users` ``, becomes a plain code block. A long line scrolls inside the block. Code inside a sentence stays inline. Claude is told to put each command it asks you to run in its own fenced block, so a [waiting item](reviews-and-waking.md#waiting-for-you) with a command can be copied at a glance. Single-line places (a card tile's note, a waiting item's one-line summary, a trace step) show the text with its Markdown marks removed. Anything longer than about 12 lines (about 16 for a note) is clamped with a fade and a **Show more** button (**Show less** folds it again) in place of an inner scroll bar; short text has no button. The note you edit stays a plain text box.

**Start as thread.** Pressing it (or **Start as thread** in the card's gear menu) opens a form at the bottom of the left pane, in place of the buttons. A card no agent has worked on shows "No agent has worked on this card" in the centre.

![The card Address autocomplete with the Start as thread form open: the session it reports to, the Worker field set to the sub-agent worker with its model and effort, Brief or Full copy, read-only or can edit files, with Start and Cancel](start-as-thread.png)

**Linking a run to a card.** The main session starts the Agent tool call's `description` with the card id in brackets, for example `[c24] fix the tax rounding`. The `board_add` reply, `/thread:track`, `/thread:add` and `/thread:board` remind Claude to do this whenever it hands a card's work to a sub-agent; you can also ask for it in words ("delegate c24, and put its id first in the description"). Two small hooks, `SubagentStart` and `SubagentStop`, notice the marker: at start they add a running run to the card, at stop they record the agent's report, step count and tokens and keep a snapshot of its steps (the stop hook waits about half a second for the agent's last transcript line, only for a run that is on a card). Both stay silent, never print into the session, and do nothing for a description without the marker, for a card that does not exist in this project, for a thread's own process, or in [chat-only mode](#chat-only-mode).

**Work of a thread on a card.** When Claude starts a thread with `card` (see [Running a lane for a card](delegation.md#running-a-lane-for-a-card)), each turn of the thread is a run on that task or idea, with no hooks involved: it is opened when the turn starts and closed when the turn is recorded. Its tile shows the lane's name (else the agent's, else "thread") and "thread c9 · turn 2"; the centre pane names the lane and gives a **Thread c9** link to the thread's own page (plain text when the thread card has been deleted), and shows the prompt the provider got (headed "Thread brief"), the steps live from the thread's own activity file, then its report; the Trace and the **working** indicator treat it like a sub-agent run. The card stays a task or idea and its done gate is unchanged. The board closes such a run itself, from the turn's own record, as soon as its thread is no longer running that turn (a poll of the board does it), and it opens a run for a turn an older plugin session added without one. **Mark as stopped** shows for such a run only in the moment before that, and the board refuses it (409) while the thread is still running that turn: end the thread instead. Its name in Summary's Work by worker is the thread's (its agent, else its lane, else `thread:<id>`), the same as the thread card's own tokens.

What is and is not shown:

- Only runs whose description starts with `[cN]` show. Work the main session does itself, and a delegation without the marker, shows nothing on the card (the card's History still shows its moves and edits).
- A card that has become a thread (Start as thread) or is a milestone does not take runs.
- What the code does for two cases nobody has seen in a live Claude Code session, so both are untested there: an agent that starts again with the same id (for example after it was sent a message) has its run reopened instead of getting a second one, and an agent started by another sub-agent is ignored.
- The steps come from the agent's own transcript, which Claude Code keeps under `~/.claude/projects/` (under `$CLAUDE_CONFIG_DIR/projects/` when that variable is set). That folder layout is not documented, so a future Claude Code version may change it and the page would then show no steps (the prompt, the report and the other figures still come from the hooks). Claude Code can also clean transcripts up, which is why a snapshot of each finished run's steps is kept in the project's logs folder (`cN.rM.activity.jsonl`, removed with the card). A long run keeps its newest 2000 steps and tool results, with a note that earlier ones are not shown; its step count is still the real one.
- The report is the text the agent handed back with Claude Code's `SubagentHandback` call (how current Claude Code returns a sub-agent's result to the main session), else the agent's last message. A run recorded by a session on a plugin version before 0.24.2 has only the last message, which current Claude Code leaves empty, so it shows no report.
- The card's record keeps only a short preview of each run's prompt and report, with the step and token figures. The full texts are files in the logs folder (`cN.rM.prompt.txt`, `cN.rM.report.txt`), which the page loads when you open the card, so a card with many runs stays small.
- **Mark as stopped.** A running run shows a small **Mark as stopped** button. If the agent's transcript has had no new activity for 10 minutes, the run also says "No activity for N min; it may have stopped." Use the button when a session was closed or crashed while the agent ran, or its stop was lost: the run becomes Ended, not successful, with a note, and nothing else on the card changes. If the agent's real stop arrives later it closes the run normally.
- The board reads only the transcript file recorded on a run, and only when it is `agent-<id>.jsonl` under `~/.claude/projects/` and not behind a symlink; it never takes a path from the page.

### Notify Claude

A card you add or edit on the board is **new from you** until Claude lists the board (`board_list`, which Claude does at natural stopping points, or when you tell it): the card shows "Claude has not seen this yet". **Notify Claude** is the way to say "look at this one now", without typing in the session. In a project kept in the repo, a card that arrived with a pull and that Claude has not listed on this machine is not "new from you" (a file cannot prove you wrote it): it is **new in the repo**, `board_list` marks it `(new in repo)`, and you can still press Notify Claude on it, since that click is made on your own board.

- **Where it is.** On a **task or idea** card that is new from you, or new in the repo: in the card's gear menu (**Notify Claude…**) and on its page, a **Notify Claude** button under the form next to **Start as thread**. It is not offered for a card Claude has already listed on this machine, for a thread or a milestone, in a [chat-only](#chat-only-mode) project, or on a read-only board. The List has no gear, so use the card's page there.
- **Which session.** Pressing it opens a small step at the bottom of the left pane with a **Session to notify** select: the sessions active in the last 7 days, most recently active first, plus the most recent one whatever its age, which is already chosen (so a session that ended long ago does not pile up in the list). **Notify** sends it; **Cancel** closes the step. A project with no session seen yet says **No recent session** and its **Notify** button stays disabled.
- **What happens.** The board stores the request on the card: a random request id (`notifyId`), the card's revision as it is at the click (`notifyForRev`, its `updatedAt`), the session (`notifySession`) and the time (`notifyRequestedAt`). This does not count as an edit and does not touch the card's history. The session you picked then gets a line with its next message, for example `The user asks you to look at card c12 "Address autocomplete" (task, New): "Suggest addresses while the customer types…". Treat it as if they had typed it; board_list with session_id "<its id>" marks it as seen.`, with the card's title and note quoted as text and the note cut to 500 characters. With [waking](reviews-and-waking.md#waking-the-session) on, an idle session wakes within a few seconds instead of waiting for your next message. At most three requests ride on one message, within the message's budget (see [How an answer reaches Claude](reviews-and-waking.md#waiting-for-you)); every other open request is named in a line (`The user also asked you to look at cards c14, c15; they come with the next message.`) and is carried by one of the next messages, those not carried yet first. A card with a request is also not counted a second time in the "new board cards from the user" line.
- **On the page.** The card shows **Claude notified** (the tooltip names the session) beside "Claude has not seen this yet", and the button becomes **Notify again**, which picks a session again and counts as a new request (it wakes the session again).
- **When it ends.** A request ends when **the session you picked** lists the board (`board_list` with its session id: the line tells Claude to pass it), or when the card is edited after the click: the request is bound to the card's revision, so any later edit ends it, whatever the clocks say (the edit is new, and nobody was told about it; notify again after an edit). In a project kept in the repo the revision is the card's `updatedAt` together with a fingerprint of what you read and set on the card (title, note, kind, stage, type, priority, labels, blocked by, acceptance criteria, milestone and lane), so a pull that changes the note (or any of those) and keeps the file's `updatedAt` ends the request too, while a waiting item that another session adds, your answer to an item, or a note about who worked on the card does not (it is not an edit of the card, as on a board kept on the machine): what you read on your board when you clicked is what Claude is told, or nothing. A request stored in an earlier form of the revision (the plain `updatedAt`) never counts as open. Another session listing the board marks the card seen for everyone ("Claude has not seen this yet" goes away) but does not end the request: **Claude notified** stays until the picked session lists it, and the line repeats with each message that session gets until then. The record of a request an older plugin version or an earlier preview wrote has no request id and is ignored.
- Over the [tunnel](security.md#opening-the-board-from-your-phone-tunnel) it works too, like answering a waiting item.

### Card fields, workers and the done gate

A task or idea card can carry more than a title and a note. Claude sets these with `board_add` and `board_update`, and you set them on the card's page on the board; none is required, and a card without them looks and works as before. Milestones take none of them. A thread card can have a type, a priority and labels, but no blockers or criteria, so a card that has acceptance criteria or a **Blocked by** list cannot be started as a thread, even when all its blockers are done (**Start as thread** is greyed out on its page, with the line "A card with acceptance criteria or a Blocked by list cannot be started as a thread; clear them first." under it; clear them, or keep it as a task). The board's List and `board_list` call a card blocked only while one of its blockers is not in the done stage or a later one.

| Field | Values |
|---|---|
| `type` | `task` (the default) or `bug`. |
| `priority` | `high`, `normal` (the default) or `low`. |
| `labels` | Up to 8 labels, each 1 to 24 characters. They are lowercased and trimmed. A repeated label is refused; the board's form drops repeats for you. |
| `blocked_by` | Up to 10 ids of other cards in the project that must be finished first. A card cannot be blocked by itself or by a milestone. A repeated id is refused. If a blocking card is deleted later, it simply drops out of the list. |
| `criteria` | Up to 10 acceptance criteria, each one line of up to 200 characters (a line break inside one is refused; give each line as its own criterion). Once a card has criteria, Claude can only add lines at the end: it cannot remove, reword or reorder them, because they are your test of the work. You change them on the board. |

Only values that differ from the default are stored. An empty value (an empty list, or an empty string) removes a field. A refused value is not saved, and the message says what is wrong. `board_list` shows the fields as short marks after the title (see [Tools Claude uses](agent-behavior.md#tools-claude-uses)). The board's card route (`PATCH /api/cards/<id>`, and `POST /api/cards` for a new card) takes the same five fields with the same checks, under the JSON keys `type`, `priority`, `labels`, `blockedBy` (camelCase, not `blocked_by`) and `criteria`, besides `title`, `note`, `status` and `parent` (and `kind` for `POST`). Both answer 400 for any other key, and the messages name the key you sent. The board may change or remove criteria freely.

**Editing the fields on the board.** A task or idea's page has the fields under Status and Milestone:

![The card Cart total drifts with two coupons: Type Bug, Priority High, labels checkout and payments, Blocked by c11 and c14 with their stages, three acceptance criteria and a Worked by list; in the centre four sub-agent runs (the analyst finds the rounding difference, the worker fixes it, the critic finds a gap with fixed-amount coupons, and a fourth run covers that gap) and the trace on the right](card.png)

- **Type** (Task, Bug or Idea) and **Priority** (High, Normal or Low). Idea turns the card into an idea and Task or Bug turns an idea back into a task: Save sends `kind` (and `type`) with the other changes, and the Kind row in the details list follows. Choosing Idea changes only the kind: a bug that you turn into an idea keeps its bug type, so it stays a bug idea (it keeps its bug mark on the Board and in the List, and counts as an open bug while it is not finished). Choosing Task clears the bug type, and choosing Bug on an idea makes it a bug task. An idea does not count towards its milestone until it is a task.
- **Labels**, separated by commas. The labels show as chips under the box as you type, lowercased and without repeats.
- **Blocked by**, the ids of the cards that must be finished first, separated by commas. Each id shows below as a link to its card with the card's stage, plus "(done)" when that stage has the done role under another name, and an id that is not a card on the board shows "No card with this id".
- **Acceptance criteria**, one line each: **Add criterion** (or Enter in a filled line) adds a line and the **×** beside a line removes it, up to 10 lines of 200 characters.

**Save** sends only the fields you changed. A value the server refuses (see [Troubleshooting](troubleshooting.md#troubleshooting)) shows its message in the error banner, saves nothing and keeps what you typed. A milestone has none of these fields (nor a Status). A thread's page has no card form, so it lists its type, priority, labels and workers as read-only rows. The new-card form takes a priority and labels, and its **Type** select (Task, Bug, Idea or Milestone) sets the type: Bug makes a task of type bug. The List sorts and filters by these fields (see [The List view](#the-list-view)), and the Summary counts open bugs.

**Who worked on a card.** The card's page shows the workers as chips in its details list (**Worked by**, read-only; hover a chip for what it is), and the List has a Worked by column. `board_add`, `board_update` and `wait_add` take an optional `worker`: `main` (the session itself), `agent:<type>` (a sub-agent), `thread:<card id>` (a side thread) or `lane:<name>` (a [delegation lane](delegation.md#delegation-lanes)). Claude is told to pass it every time. It is written into the history entries that call creates; `wait_add` adds an entry only when it is given a worker, and a `board_update` that changes nothing but the worker adds an entry of type `worked`, unless the latest entry already names that worker (thread cards get none). (A page of version 0.11.0 or earlier skips history entries of a type it does not know, so these are safe to leave in the data.) The board's data for each card also carries a `workedBy` list, built from those entries, from the sub-agent runs linked to the card, and for a thread from its agent or lane: each worker once, in the order they first appear. A very long agent or lane name is cut to fit the 64 characters a worker may have rather than left out.

**The done gate.** A card that has `criteria` cannot be moved by Claude into the stage with the **done** role until you have approved it:

- the card's latest closed review item (see [Waiting for you](reviews-and-waking.md#waiting-for-you)) must have been answered **Approve** on the board, and
- no review item on the card may still be open.

"Closed" means answered or withdrawn, and the latest one by the time it was closed decides. So if you approved one review, Claude then opened a second and withdrew it, the card is not approved; it needs a new approval. A review answered with **Request changes**, or closed with "answered in the chat" (which holds no verdict), does not count either. Only reviews closed after the card last left the finished stages count, so moving an approved card back out of Done and the stages after it (by you or by Claude) takes the approval away. Moving it from Done to Released, or between any two finished stages, does not. The card itself records when it left the finished stages (`leftDoneAt`), so this does not depend on its history, which keeps only the last 50 entries; for a move that an older plugin version made, which leaves no such record, the history is read as well. Version 0.12.1 and older recorded `leftDoneAt` for a move from Done to Released too, so such a card needs a new approval here: stricter, never looser. If an approval and a withdrawal are closed in the very same millisecond, the withdrawal wins. Changing the criteria does not take an approval away. Claude's way through is to raise a review item with `wait_add` (kind `review`) and to move the card after you approve. The gate follows your stages: it covers the stage with the done role, whatever it is called, and every stage after it. Claude cannot move a card with criteria into any of them, or add one there, until you approve it, and cannot move a card you dragged there unverified from one of them to another.

**In a project kept in the repo, only approvals given on this machine count.** A repo file can be edited by anyone who can commit, and a review item in it can say it was approved. So the gate counts an approval for Claude only when this machine has its own record of it, in the data directory (the item's id, when it was answered, and a fingerprint of the card's acceptance criteria): the record is made when you press **Approve** on this machine's board, with **Send** for one answer or for a batch. It is never written to the repo file. The existing rules still apply on top (the latest closed review, none open, closed after the card last left the finished stages). Changing a card's criteria afterwards needs a new approval. An approval that only the repo file has, for a review item this machine has no record of at all (it was given on another computer), shows on the card page as **Approved on another device** with a **Confirm approval** button; until you press it, Claude's `board_update` and `board_remove` treat the card as not approved, and the card shows as not verified when it sits in a finished stage. If this machine does have a record of that review, and the card's acceptance criteria are not the ones you approved (a pull changed them, or you did), the card shows **Criteria changed since your approval** instead, with the current criteria listed next to the same button: confirming records the approval for the criteria as they are. Reopening a card is remembered on this machine too (when the card last left the finished stages, in the data directory): a pushed file that drops the card's own record of the exit and the moves from its history cannot make an approval given before the reopening count again, and the approvals recorded here before the exit are dropped with it. This machine also remembers that it saw the card in a finished stage: when a pull then reopens the card and wipes every trace of the exit in the same step, nothing counts for it until the next write on this machine notices (which pins the exit and drops the old approvals), so the approval of before is not replayed. **A file is never believed about time.** A date in a card file that is later than now (plus 5 minutes, for clocks that differ) is treated as absent: a `leftDoneAt`, a move in the history or a withdrawn review dated far ahead is neither an exit nor a review that outranks yours, so it cannot lock the card or hide an exit. An approval is placed against the card's exits by the time this machine recorded it (when you pressed Approve, or **Confirm approval**), never by the date the file gives it; an exit that a file dates a few minutes ahead of this machine (a clock that differs) is pinned as now, the moment this machine saw it, and an approval you give a moment later is placed just after it (it keeps its true time), so it still counts, today and after that date has passed; an exit the file dates after your approval still ends it. **A review you answered here is remembered.** This machine keeps your answers to review items (a "changes" as well as an approval) with their time and a fingerprint of the answer, and keeps the record of a review item that has gone from the file. If an answer you gave here at or after the approval is missing from the file, or the file holds another time, verdict or comment for it (someone removed your "changes" review, back-dated it, or turned it into another kind of item such as a question, so that an older approval would be the latest again; or the approved item itself was re-dated), the older approval does not count: the card page says **Review changed in the repo file**, with the same **Confirm approval** button, and `board_update` and `board_remove` treat the card as not approved until you confirm it again on this board or answer a new review. **Criteria dropped in the file.** This machine keeps how many acceptance criteria the card had on your board (and a fingerprint of them). A pull that removes the criteria, or cuts them to fewer, does not turn the gate off: the card page says **Criteria cut in the repo file**, the card is still held to the gate (`board_update` is refused with that reason, `board_list` marks `[criteria 0, cut in the repo file: the owner must confirm on the board]`), and Claude cannot change those criteria or remove the card. You accept the change on this board by editing the criteria there (add a line and save, then remove it and save again): that sets the record to what you saved. **Confirm approval confirms what the card page showed.** The click sends the review item, the time it was answered and a fingerprint of the acceptance criteria that the page displayed; if the repo file has another review, another answer time or other criteria by then (a pull landed between the page and your click), nothing is recorded, the board says the card changed since you looked at it, and the card is shown again to read and confirm anew. The button writes only the local record (it is also available through the [tunnel](security.md#opening-the-board-from-your-phone-tunnel)). The approval of a card in this machine's older boards (made by a session on an older plugin version before the board moved into the repo) is recorded locally when the card is copied or imported, since it came from this machine's own store. A project that keeps its board on the machine behaves as before.

The board itself is never held to the gate: you can drag a card with criteria to the done column at any time. Such a card (in the Done stage or a later one) is shown as **not verified** (`verified: false` in the board's data, and `(done, not verified)` in `board_list`) until a review of it is approved. On the board its face has a **not verified** tag, its page has a **Done, not verified** note ("Claude may not move it to done or a later stage until you approve a review item; you moved it yourself."), and the List's **Done, not verified** button finds such cards. A card moved there by a session on an older plugin version is marked the same way, and so is a thread card that has criteria and has ended (version 0.11.0 could start a thread from a card with criteria; `board_remove` holds such a thread to the same rule as a task, while `thread_end` is not held). The mark is worked out when the card is read, never stored.

![The card Invoice PDF for every order in the Done stage, with the note Done, not verified above its Milestone field, and three acceptance criteria below](not-verified.png)

Each project in the board's project list also carries counts of its cards: `open` (not in the Done stage or a later one, milestones left out), `done` and `waiting`. They fill the tiles on the [projects home](#projects-home-and-top-bar).


### Full access

Under the fields, a saved task or idea has an **Allow full access** switch, with the line "A worker started for this card may run any command as you, with no sandbox: the GPU, the network, every file." It is the only way to let a worker run in [mode `full`](threads.md#how-threads-work) (no sandbox, no permission checks, for example to render video on the GPU).

- **It is yours alone.** **Save** sends it with the other changes (`allowFull`), and only the board on this computer takes it. Claude's tools do not: `board_add` and `board_update` refuse a call that names it, with a message that says so, and nothing is written. The phone link (the [tunnel](security.md#opening-the-board-from-your-phone-tunnel)) cannot turn it on or take it away either: a save that carries it is refused whole with a message that says so, and the switch is shown disabled there. A new card has no switch (save it first), and neither does a milestone. It is read-only while the board is read-only (the project's folder was not found).
- **It belongs to this machine.** Like an approval, it is never written into a card file of a project [kept in the repo](storage-and-sync.md#keeping-the-board-in-your-repo-claudethread): it stays in this machine's own record, and a card file that says `allowFull` is read as if it did not. A pull from someone else cannot give your machine full access. The card's History says "You allowed full access" or "You took full access away" (that line is shared like any history line, and is only text).
- **What it opens.** `thread_start` with mode `full` for this card, and **Full access** in the start step. A card started as a thread keeps the switch (the card itself becomes the thread), and its thread page then has a **Take away full access** button (off only: it sends the same save, and is disabled on a read-only board and through the phone link). A thread that works for a card shows the button too while it runs with full access, and it takes the switch away on that card. The switch is checked again at each follow-up and when each turn launches, so taking it away stops the next turn; a turn that is already running is not stopped (end the thread for that). The thread page's message box says why when a full-access thread can no longer take a follow-up. A card page shows the **Full access** tag in its header while the switch is on, and `board_list` marks the card `{full access allowed}`.
- **It is for the text it was allowed for.** The board keeps, on this machine only, a fingerprint of the card's title and note when you allow it. If they change afterwards, by a collaborator's push or by Claude editing the note, the switch counts as off: `thread_start` and **Start as thread** refuse with "full access was allowed for c12 before its title or note changed: the user must allow it again", a full-access thread of that card cannot take a follow-up, the card page shows the switch unticked with "Needs to be allowed again", and `board_list` marks the card. Tick it again and **Save** to allow the card as it is now. An edit you make yourself on the board keeps it allowed (for the new text), and so does an edit in the same save as ticking it; a save of something else on a card that needs it again does not allow it. A card that was started as a thread is not bound to its text (its task was fixed when it started).
- **Where a thread shows it.** A thread's page says **Full access** in its header and, for a lane thread, in its Access row; `thread_status` says "mode full (full access: no sandbox, no permission checks)".

### Card and waiting item links

In any Markdown text on the board (a note, a waiting item, a run's prompt or report, a thread's messages), a **card id** such as `c37` or `c8k2x1`, or a **waiting item id** such as `c37.w2`, becomes a link when that card (and, for an item, that item) is on the project's board. A link to a card's page on this board (a web address on `127.0.0.1` or `localhost` with any port, or on the host of the page itself, with `#/<project>/<card id>`, bare or in `[text](…)`) is shown the same way as the id when that card is in the open project. Any other link to this board opens in this tab, never in a new one where the access token would be missing: a card that is not there or one of another project, and any other page of the board (`#/<project>/board`). A `127.0.0.1` or `localhost` address counts as the board only when it looks like a board link (it carries a board token, or its path is `/` with a `#/…` route); any other local address, such as a dev server's page on `localhost:3000`, is an ordinary link that opens in a new tab. The access token (`?t=…`, `&t=…` or `#t=…`) is cut out of every address the board shows, in every kind of text, for any host, and is never kept in a link. Ids with no such card or item, ids inside a web address, an e-mail, a file path or an assignment (`x=c37`), and ids inside `code` or link text stay plain text, and single-line places (a tile, a chip, a list cell) show them as text too. In a chat-only project only thread cards are linked, and no item is. On a thread's own page the links are made the same way, but its text is not redrawn when a card or item appears later, so an id that was not yet on the board when the page opened becomes a link only when you open the page again. Following a link from a card page with unsaved edits asks first: **Discard changes** then goes on to the card you followed, **Keep editing** stays.

- **Preview.** Hover a link for about a third of a second, or tab to it, and a small card opens below it. For a card it shows the kind, the id, the title, the stage and how many items wait for you; for an item, its kind, id, state (open, answered or withdrawn), about the first 160 characters of its text, and the card it is on. A milestone shows its number of cards instead of a stage. It closes when the pointer leaves (you can move into it), on **Esc**, when focus leaves and when the page scrolls. **Tab** from the link goes to the preview's **Visit** button. On a touch screen there is no preview: a tap goes straight to the card.
- **Visit** (or a click or **Enter** on the link) opens the card's page. For an item it also scrolls to that item, moves focus to it and marks it for a moment (a still outline when you have asked for reduced motion); a closed item is opened in "Earlier items" first. A click with a modifier key (new tab) is the browser's own.

Claude is told, in the `note` description of `board_add` and `board_update`, that the board shows Markdown, to write a long note as short sections (a `###` heading or a bold lead for each part, lists on their own lines), and that an id in the text becomes a link.

## Milestones

A **milestone** is a card that groups other cards. Tasks, ideas and threads can sit under it, so you can see one piece of work as a whole: what is in it, and how much is done. Without milestones the board is a flat list.

![The page of the milestone Launch v1: its title and note, its state and progress bar at 7 of 15 done, Copy report, and its cards grouped by stage](milestone.png)

- **One level only.** A milestone cannot sit under another milestone, and only a milestone can be a parent. Every other card (task, idea or thread) can have at most one milestone.
- **A milestone has no stage.** It has a title and a note, and its state comes from its cards: **Empty** when it has no counted card, **Open** while some counted card is not finished, **Done** when every counted card is finished. It reopens by itself when a card is added to it or a card leaves done. Nobody sets a state by hand: `board_update` and the board refuse a `status` on a milestone ("a milestone has no stage: it is done when all its cards are done"). A milestone is not on the Board's columns; the Milestones view, the List and the Summary show it. A milestone cannot be started as a thread.
- **The tag.** A card under a milestone shows the milestone's title in square brackets after its title, such as `[Ship the invoice export]`, clipped to 30 characters. On the board it is a tag you can click to filter the board to that milestone.
- **Progress.** A milestone shows `3/5 done`: the cards under it that are finished, out of the cards that count. **Ideas do not count** until they become tasks. A card is finished when it is in the **done** role's stage (by default Done) or in any stage after it in your stage order (for example Released). A thread is finished once it has ended, not when a turn has finished. (If you point the **review** and **done** roles at the same stage, a finished turn counts too.) Milestones that an older version stored with a stage keep it in the data, and it is ignored.
- **Filtering the board.** The toolbar has a **Milestone** select (its first option is "All milestones", then each milestone by title, then No milestone). It appears once a milestone exists and combines with search, the session filter and the threads-only filter. It shows the cards under the milestone. The Waiting view and the List have the same select.
- **The Milestones view.** The top bar's **Milestones** view shows every milestone at a glance, in number order, as a map of which milestone depends on which (from its cards' Blocked by and the links you draw), with its state, its progress and its open cards; see [The Milestones view](#the-milestones-view).
- **The report.** `/thread:board --parent <id>` prints the report for one milestone: a summary line with its state, then the milestone and its cards grouped by stage. On the board, open the milestone: its page lists "Cards in this milestone" grouped by stage, each row linking to that card, and **Copy report** copies the same list as plain text.

### Flags

| Where | Flag | Effect |
|---|---|---|
| `/thread:add` | `--milestone` | The new card is a milestone. |
| `/thread:add` | `--parent <id>` | The new card goes under the milestone with this id. |
| `/thread:new` | `--parent <id>` | The thread goes under the milestone with this id. |
| `/thread:board` | `--parent <id>` | Show the report for this milestone. |

Without `--parent`, you can name a milestone in words ("add this to the invoice export milestone") and Claude finds its id with `board_list`. To put an existing card under a milestone, or take it out, ask Claude, or use the **Milestone** select on the card's page on the board, or **Set milestone** in the card's gear menu. Removing a milestone does not remove its cards; they stay, without a milestone.

### A worked example

```text
/thread:add --milestone Ship the invoice export
/thread:add --parent c12 write the CSV exporter
/thread:add --parent c12 idea: offer an Excel export too
/thread:new --parent c12 check how the export behaves with 100,000 rows
```

The milestone is `c12`. The task and the idea start in New. The idea does not count towards the milestone, so it is 1 of 2 done: the thread and the CSV task. After the thread has run and been ended, and the CSV task has moved to In progress, `/thread:board --parent c12` gives a report built from this list:

```text
Milestone c12 "Ship the invoice export": open, 1 of 2 done.
New (1)
- c14 [idea] Offer an Excel export too [Ship the invoice export]
In progress (1)
- c13 [task] Write the CSV exporter [Ship the invoice export]
Done (1)
- c15 [thread:ended] Check how the export behaves with 100,000 rows [Ship the invoice export]
Milestones (1)
- c12 [milestone:open] Ship the invoice export (1/2 done)

Stages, as id: label [what the plugin uses it for]:
- idea: Idea
- new: New [start]
- in_progress: In progress [working]
- review: Review [review]
- blocked: Blocked [blocked]
- done: Done [done]
```

The last block is how Claude knows your stage ids and which stage is used for what; it is there for every board, including an empty one.

`/thread:board` on its own prints the same kind of list for the whole board: the stages, then the **Milestones** section with each milestone's state and progress, and the tags.

The errors are plain: `milestone not found: c9`, `c3 is not a milestone`, `a milestone cannot have a parent`.

## Custom stages

The **stages** are the board's columns. The default six, in order:

| Id | Label |
|---|---|
| `idea` | Idea |
| `new` | New |
| `in_progress` | In progress |
| `review` | Review |
| `blocked` | Blocked |
| `done` | Done |

You can replace them with your own, set with `/thread:setup` (global or per project). The limits:

- 2 to 10 stages.
- Each **id** is lowercase letters, digits and underscores, starts with a letter, and is at most 24 characters. Ids are unique. `to_do` and `in_review` are valid; `Done`, `2nd` and `in progress` are not.
- Each **label** is the name shown on the board and in lists: 1 to 30 characters after trimming.
- Cards keep the id of the stage they are in, not its label, so you can rename a label without moving any card.

![The Board of a project with four stages of its own: To do, Doing, Checking and Done](stages.png)

### Roles

Some of the plugin's own behaviour has to know which stage means what. The **roles** say so. Each role points to one stage id.

| Role | Used for |
|---|---|
| `start` | Where a new card lands when no stage is given. Also where a card is shown when its own stage no longer exists. |
| `working` | A thread whose turn is running. |
| `review` | A thread whose turn has finished, waiting for you to look. |
| `blocked` | A thread that failed. |
| `done` | A thread that was ended. Also where a milestone counts a card as finished: this stage and any stage after it. |

Thread cards follow their thread through these roles; you do not move them by hand. Several roles can point to the same stage.

**Default roles.** With the six default ids, in the default order (their labels may differ), the roles are `start` New, `working` In progress, `review` Review, `blocked` Blocked, `done` Done. With your own stages, when you give no roles, the plugin uses the order (n is the number of stages):

| Role | Stage |
|---|---|
| `start` | the first |
| `working` | the second (the first when there are only two) |
| `review` | the second to last when n is more than 2, else the last |
| `blocked` | the same as `working` |
| `done` | the last |

For the four stages in the example above that gives start To do, working Doing, review Checking, blocked Doing, done Done. A `roles` object that names only some roles is filled in from this table (or from the default roles, when the stage ids are the six default ids in the default order). Roles belong to the stages in the same file: a file with `roles` must also list its `stages`. Giving new stages without roles drops the old roles, so they are never carried over to stages that may not exist. Changing some roles later keeps the others.

### Cards whose stage was removed

When you change the stages, a card may be left with a stage that no longer exists. It is not moved and nothing in the data is rewritten. It is *shown* in the **start** stage. If you bring the stage id back, the card returns to it. Moving the card yourself writes its new stage. A thread card is different: it is always shown in the stage for its current state, so it follows a change of roles at once. The result of a setup that changes the stages says how many cards of the current project are in this state; a global change can affect other projects too, and those are not counted.

## Chat-only mode

If all you want is side threads, you can switch the task board off. Run `/thread:setup` and choose threads only, for every project or for one.

**What is switched off.**

- Adding cards. `board_add` and `/thread:add` are refused with "The task board is off for this project (chat-only). Run /thread:setup to turn it on." On the board page, adding a card is refused the same way (HTTP status 409), and the **New card** button is not shown.
- Editing and removing task, idea and milestone cards. They give the same message.
- Starting a card as a thread from the board, since no task cards are shown.
- The note on your next message that tells Claude about new cards you added on the board.
- `board_list` lists thread cards only and says in a line that the project is chat-only.

**What still works.** Everything about threads: `/thread:new`, `/thread:continue`, `/thread:report`, `/thread:status`, `/thread:end`, the board page with thread cards, full-window threads, follow-ups from the board, and `/thread:board`. Thread cards can still be updated and removed. On the board, only thread cards are shown, in three fixed columns, **New**, **Review** and **Done**, whatever stages the task board has: a running thread is in New, a thread whose turn finished or failed is in Review, an ended thread is in Done. The project has no Summary, List, Milestones or Waiting view, so its top bar has **Board** only, and its tile on the projects home is marked chat-only once you have opened the project. A one-line note under the toolbar says that the task board is off and `/thread:setup` turns it on. The stages you set for the task board are kept as they are (`config_get` shows both) and come back when you turn the board on. [Waiting items](reviews-and-waking.md#waiting-for-you) are not shown.

**Nothing is deleted.** Cards that already exist stay in the project's state file. Turn the board back on and they reappear.

**To turn the task board back on.** Run `/thread:setup` and choose threads plus the task board. If chat-only comes from a settings file you no longer want, `/thread:setup --reset` for that scope also works. `/thread:setup --show` tells you which file the mode came from. Or set `"mode": "tasks"` in the file.

## Setup

`/thread:setup` lets you choose how the plugin behaves. You do not have to run it. If you never do, everything works with the defaults: the task board is on, with six stages.

Claude runs it as a short conversation, one question at a time, using Claude Code's question popup when the client has one. Each choice comes with a one-line explanation, and the default is listed first. It asks:

1. **Where the setting applies.** Every project (global), or only this project. Either way, cards and threads are always stored per project; this choice only decides where the *settings* live.
2. **What you use thread for.** Threads only ([chat-only](#chat-only-mode): side threads, no task board), or threads plus the task board (cards, ideas and milestones).
3. **Stages, only for the task board.** The default six, or your own. If your own, you describe how you work in your own words and Claude helps you design the stages. It proposes 2 to 10 stages, each with a short id and a label, and says in plain words which stage each part of the plugin will use: "a new card lands in To do", "a running thread sits in Doing". You change the list until you agree. See [Custom stages](#custom-stages) for the rules.

4. **Waking.** Whether an answer, a report click or a Notify Claude click on the board should wake an idle session (default: no). See [Waking the session](reviews-and-waking.md#waking-the-session) before you say yes: a woken session acts without you. If you say yes, Claude shows you what it does once more and saves only after you agree again.
5. **Where this project's cards are kept.** On this machine (the default), or [in the repo](storage-and-sync.md#keeping-the-board-in-your-repo-claudethread), as files in a `.claude/thread/` folder that you commit. Claude says what that means before it turns it on, and it is a per-project choice. Skipped when the project already keeps its board in the repo.
6. **Code map.** Whether new threads should use a [Graphify code map](threads.md#code-maps-graphify) when the project has one (default: no). Claude says in one sentence what it does and the risk (a map built before recent changes can miss code, so the thread is told to confirm in the files), and that you install Graphify yourself.

7. **Update check.** Whether thread may check GitHub once a day for a new release (default: no). Claude says in one sentence that this is the only network call thread makes besides the optional tunnel, and saves it only after you agree again. See [Staying up to date](configuration.md#staying-up-to-date) and [the update check](security.md#the-update-check). Claude also tells you that auto-update can only be turned on by you, in `/plugin`.

Then Claude saves the settings, reports the result in a few lines, and tells you that `/thread:setup` can be run again at any time. Setup never changes a card; moving the cards into the repo copies them (the first time only) and leaves the originals where they were.

```text
/thread:setup            the conversation above
/thread:setup --show     print the current settings and stop
/thread:setup --reset    ask which settings to delete (every project, or this one), delete that file, and stop
```

`--show` prints the mode, whether waking is on, the stages in order, the role of each stage, where each setting came from (default, the global file, or the project file), and the paths of both files. `--reset` deletes one settings file; cards and threads are not touched, and the plugin falls back to the other file, or to the defaults.

**The one-time hint.** In the first session after you install the plugin, Claude is told that the plugin has not been set up and, when it does not interrupt your request, mentions `/thread:setup` once. This happens once per machine, and only while no settings file exists. If you ignore it, the plugin carries on with the defaults and does not mention it again.

The settings files, and every field they take, are described in [Where the settings live](configuration.md#where-the-settings-live).
