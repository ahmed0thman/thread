# Delegation lanes

Part of the thread documentation: [index](README.md).

A **lane** is a named setting from the separate [delegate skills](https://github.com/amElnagdy/delegate-skills), written by [Ahmed Nagdy](https://github.com/amElnagdy): which coding CLI does a job (the provider: `codex`, `agy`, `opencode` or `claude`), on which model, at which effort (or variant), and whether it may only read. Names such as `code-codex` or `ui-design` are yours to choose. A thread can run on a lane, and so can a task card that has one. This plugin only reads the lane config; it never writes it or its approval.

- **Where lanes come from.** The delegate skills keep them in `~/.config/delegate-skills/config.json` (all projects) and `<git root>/.delegate/config.json` (one project). The plugin asks the `delegate-setup` skill's script, `~/.claude/skills/delegate-setup/scripts/config.mjs load`, for the lanes in effect in the project, and keeps the answer for about 30 seconds. Running a thread uses the provider's relay, `~/.claude/skills/<provider>-delegate/scripts/relay.mjs`, which the same skills provide. Set `THREAD_DELEGATE_DIR` if the skills live elsewhere. Lanes whose provider is not one of the four above are left out.
- **They need the delegate skills.** Without them (or when the script fails or takes too long) the board shows nothing about lanes, `lane_list` says they are not installed, and a lane is refused. A card that already has a lane still shows its tag, marked **not found**.
- **A project's lane config must be approved.** A lane that comes from `.delegate/config.json` is usable only after you approve that file with the `delegate-setup` skill. Until then its lanes are **not approved**: nothing can be started or continued on one.

## Starting a thread on a lane

```text
/thread:new --lane code-codex find why the invoice total is off by a cent
/thread:new --lane review-ro --parent c12 review the retry logic
```

`--lane <name>` (the `lane` argument of `thread_start`) runs the thread on that lane. Claude can also choose a lane itself: it calls `lane_list` and passes a lane only when you or the project's instructions (your `CLAUDE.md`, for example) say which lanes suit which work; otherwise it keeps choosing the agent and model as described in [Choosing the agent and model](agent-behavior.md#choosing-the-agent-and-model).

- **What it runs.** A lane thread starts a fresh session on the lane's provider, with the same brief and task a normal thread gets, read-only unless you ask for write (`--write`). The plugin starts the provider's relay (`node <relay> --brief <file> --cd <project> --lane <name> --out-dir <logs folder> --timeout <the turn limit>`, plus `--read-only` for read mode; a codex lane in write mode passes `--sandbox <the lane's sandbox, or workspace-write>` on every turn (an opencode lane in write mode runs without a sandbox, and so does a codex lane whose sandbox is `danger-full-access`), since codex applies a sandbox on a resumed turn only when one is passed) in the background. The plugin passes the brief in a file under the project's logs folder, never in its own arguments. A read-mode turn's prompt also says that the run is read-only and that the answer should come from reading and reporting, without trying to leave plan mode (the `claude` relay enforces read-only with plan mode). The `agy` relay, though, hands the brief to the `agy` program as an argument, so other programs on your machine can see it in the process list while an agy turn runs. The plugin never passes `--skip-git-repo-check`, and passes a flag that skips permissions or the sandbox only for a thread in [full-access mode](#full-access-on-a-lane), which needs your switch on the card. When the relay exits, its `result.json` decides the turn: `completed` is a finished turn and its report is the result (or, if the provider wrote none, a one-line stand-in); anything else, or no result at all, is a failed turn. Its error is the status, then the relay's own error, else the last line of the provider's stderr, else the last failure the provider wrote into the turn's `events.jsonl` (codex's `turn.failed`, for example a model your account does not support), else the first line the relay itself printed, for example `codex failed: Not inside a trusted directory and --skip-git-repo-check was not specified.` (codex refuses to run outside a git repository).
- **Files the provider reports.** On a read-only turn, if the provider's relay reports that files may have changed (its read-only check is a tripwire for `agy` and `claude`, and an incomplete check counts too), the turn's report starts with one plain line saying so. On a write turn the report starts with one line, "Uncommitted changes in the working tree after this turn (from the relay): …", and the read-only line carries the same list. The relay builds that list from `git status` after the run, so it is everything uncommitted in the working tree, including changes from earlier turns and other threads, not only what this turn did. It shows up to eight names. `codex` and `opencode` read-only runs are enforced by the provider and report nothing of this kind.
- **Limits.** A lane cannot be combined with `--agent`, `--model`, `--effort` or `--full` (a copy of the conversation), and has no extra folders (`extra_dirs`). A **write** thread needs a lane that can edit files, and **agy lanes are read-only in this version**: agy's headless mode auto-denies every edit, and the only remedy is a flag that skips permissions, which the plugin passes only in [full-access mode](#full-access-on-a-lane) (so an agy lane can be started in full access, for a card you allowed it on, and is refused in write mode). A lane whose sandbox is `danger-full-access` is shown as "Full access (no sandbox)". A lane that is read-only (`readOnly`, or a codex sandbox of `read-only`) is refused in full-access mode as in write mode. Each of these is refused with a one-line message, as is a lane that is unknown, not approved, or whose provider's relay is not installed.
- **Follow-ups.** `/thread:continue` resumes the provider's own session, whose id is stored when a turn ends (on a failed turn too). The lane is read again at the start of each follow-up, so a changed model or effort applies; a lane that is now unknown, not approved, read-only for a write thread or missing its relay is refused with the same messages as on start, and so is one that now runs on another provider. Some providers can give no session (`agy` sometimes): that thread finishes its turn, but cannot be continued ("start a new thread instead").
- **Report and end.** `/thread:report` gives the digest as for any thread, with the lane named in its header. `/thread:end`, and a stop from the board, send SIGTERM to the relay, which stops the provider's process and writes its result; the thread's card moves to the done stage as usual. A turn also stops at its time limit (`THREAD_TIMEOUT_MS`, 20 minutes by default, passed to the relay as `--timeout`; the plugin's own limit sits a little after it).
- **What you see per provider.** Lane threads on `codex`, `opencode` and `claude` show live text, tools and results in the Trace while the turn runs, refreshed about once a second. Each tool counts as one step. A `claude` lane also gives the turn its token use, as before; codex and opencode have no token counts. An `agy` lane shows start, stop and report only, with no live activity or step counts.
- **Session hooks.** A claude lane starts a child `claude` session through the relay. It carries the same mark as a thread's own process (`THREAD_DEPTH=1`), so this plugin's hooks do not register it as a main session or show it the setup hint.

## Full access on a lane

A thread started in mode `full` runs with no sandbox and no permission checks. Two lanes already run without a sandbox in write mode, and need no switch for that: an `opencode` lane (a build run passes `--auto` and opencode has no sandbox) and a `codex` lane configured with `danger-full-access`. Full access is what lifts the sandbox for the other lanes (a `codex` lane with its own sandbox, `claude`, `agy`) and for Claude threads. It needs a card that you allowed it on (see [Full access](board.md#full-access) and [Security](security.md#full-access)): `thread_start` with `mode: "full"` and the `card`, or **Full access** in the start step on the board. What the plugin asks of each provider's relay:

| Lane provider | Write mode | Full-access mode |
|---|---|---|
| `codex` | `--sandbox <the lane's sandbox, or workspace-write>` | `--sandbox danger-full-access` |
| `claude` | (no flag; the relay's default) | `--dangerously-skip-permissions` |
| `agy` | refused: read-only in this version | `--dangerously-skip-permissions` |
| `opencode` | the relay's default: a build run passes `--auto` | the same as write mode: opencode has no sandbox |

Every turn of the thread passes the flag again, a follow-up included, and a follow-up is refused when you have taken the switch away from the card. A read-only lane is refused in full-access mode like in write mode. The turn's report starts with the same one line about uncommitted files as a write turn. The provider's own terms and permission rules still apply to what it sends and does; the plugin only passes the flag.

## Putting a lane on a card

`/thread:add --lane code-codex fix the rounding bug`, or ask Claude in plain words; `board_update` changes it and an empty lane removes it. Only tasks and ideas can have a lane, not milestones, and not threads (a thread gets its lane when it starts). A name that is not a loaded lane is refused with the list of valid names. On the board you pick a card's lane in the **Worker** field of its page, or in the start step (see [Choosing a worker on the board](#choosing-a-worker-on-the-board)); the board only picks among the lanes that exist, it never edits the lane config.

A card can also be given a **sub-agent** instead (`agent` in `board_add` and `board_update`: the name of a file in `.claude/agents` of the project or of your own folder). Starting it as a thread then runs the thread as that sub-agent, as `/thread:new --agent` does. A card holds one worker, a lane or an agent: giving one takes the other off, and giving both in one call is refused. An unknown agent is refused with the list of the ones there are; a milestone and a thread cannot have one. `board_list` shows it as `{agent: reviewer}`, as a lane shows as `{lane: code-codex}`.

When a card with a lane is started as a thread with **Start as thread** on the board, it runs on that lane: the server takes the lane from the card, never from the start request (a worker chosen in the start step is saved on the card first, see below). The thread then holds the lane, and the card no longer has a separate one. A card with an agent starts the same way, as a thread run as that agent.

## Running a lane for a card

A thread, on a lane or not, can do the work of a task or idea without turning the card into a thread. Pass `card` to `thread_start` (`/thread:new --card c12 ...`; the server instructions tell Claude to pass it when a thread or lane does a card's work, and to hand a card to a lane this way rather than run a delegate skill's relay itself). The thread is a new card of its own, as always, and the task or idea shows its work the way it shows a Claude sub-agent's:

- Each turn of the thread is a **run** on the card: running while the turn runs, then done, or stopped when the turn failed or was ended. It carries the lane's name (or the agent's, or "thread"), the prompt the provider was given, the live steps in the card's Trace, and the provider's report when the turn ends. The card's tile shows the **working** indicator while a run is running. A follow-up (`/thread:continue`) adds the next run.
- The card stays a task or idea. Its acceptance criteria and its [done gate](board.md#card-fields-workers-and-the-done-gate) are unchanged: the thread's report is not an approval, and the card is not moved for you.
- A run's steps are kept in the logs folder when its turn ends, so they stay when the thread's own card is removed. `thread_status` lists the thread as `for c12`.
- The call is refused for a milestone, for a thread, for an id that is not on the board, and in [chat-only mode](board.md#chat-only-mode).
- Only lane work started this way shows on the card. When Claude runs a `*-delegate` skill's `relay.mjs` itself from the shell (the skill's own way of working), the plugin never sees that run: the card gets no working indicator, no steps and no report. Claude is told not to do that for a card, but it is an instruction, not a check; if a card shows nothing while a lane works on it, ask Claude to start the lane with `thread_start` and `card` instead.
- A run is closed by the thread's runner when the turn is recorded. In a project [kept in the repo](storage-and-sync.md#what-is-in-the-repo-and-what-stays-on-the-machine) the runner works only on the thread's own store, so the board closes the run the next time it reads the project (every request of an open board page does). A run whose thread is gone or is not running that turn is closed then too, with a note. Runs are never written into the repo's card file.

## Choosing a worker on the board

A task or idea's page has a **Worker** field in the card's form, and the **Start as thread** step has the same one. The step's field shows the worker the step will run: `Claude (default)` (the session's own model), `agent: reviewer` for a sub-agent, or the lane as `code-codex · codex · gpt-5 · high`. Pressing it opens a dialog, **Choose a worker**.

**What the card page's field shows.** The field shows who works on the card, not only the worker saved on it, in this order:

1. Something running on the card now: the sub-agent Claude handed it to, as `deep-analyst · working now` with the live dot (several running at once: `3 agents working`). A run that has gone quiet (no activity for a long time, it may have stopped) is shown muted with the ring, as `deep-analyst · quiet`, never as working now.
2. Else the saved worker (the one **Start as thread** uses), as before.
3. Else the last worker Claude used on the card: the newest of its sub-agent runs and of the workers it recorded with `board_update` or `board_add` (`worker: "agent:<type>"` or `"lane:<name>"`; `main` and threads are left out), shown muted as `deep-analyst · last used`.
4. Else `Claude (default)`.

When what the field shows is not the saved worker, a caption under it says what **Start as thread** uses, such as "Start as thread uses: Claude (default)" (a saved sub-agent that is the one running needs no caption). The tooltip has the details: each agent type and how long it has run, or when the last worker was used and whether it is a sub-agent or a lane, the saved worker, and what Start uses. This only describes: the saved worker is still what the dialog sets and what **Save** stores. A worker you picked in the dialog and have not saved yet is shown as picked. In the dialog, the row of a worker that is working now carries a **Working now** badge and the last one used a **Last used** badge (when it is listed there; a built-in agent such as `general-purpose` or `Explore` is not a file in `.claude/agents`, so it has no row).

**What the dialog has:**

- **Claude (default)** is pinned at the top: it takes the lane or agent off the card and runs on the session's own model.
- Three tabs follow, each with its count: **Sub-agents** (the files in `.claude/agents` of the project and of your own folder; each row shows the description's first line and whether it is defined in the *project* or by the *user*), **Project lanes** (from the project's lane config) and **Global lanes** (from your own, for every project). A row shows the name, then `provider · model · effort` (a sub-agent's provider is `claude`), and badges: **Read-only** (a read-only lane, and every agy lane; on an agy lane the hover text says it is read-only except with [full access](#full-access-on-a-lane)), **Overrides global** (a project lane that replaces a global lane of the same name), **Not approved** (a project lane whose config you have not approved yet; it cannot be picked, and the row says to approve it with the `delegate-setup` skill) and **Relay not installed** (the provider's `<provider>-delegate` skill is missing; it cannot be picked, and the row says which to install). The dialog opens on the tab of the chosen worker, else of the one working on the card now, else of the last one used, and its badges say which is which: on the card's page **Saved** marks the worker saved on the card (none when nothing is saved: the card then falls back to the last worker used, as its field shows, and Claude (default) gets no badge) and **Picked** one you chose and have not saved yet; in the start step **Selected** marks what **Start** runs; **Working now** and **Last used** come from the card's runs and history.
- One **search box** at the top filters all three tabs by name, provider or model (case-insensitive, a part of the word is enough). It keeps its text when you change tab, and each tab's count becomes its number of matches.
- Picking a row closes the dialog and sets the field. On the card's page the form is then changed: **Save** stores it with the rest of the card (it sends only what changed: a lane, an agent, or `null` for **Claude (default)**; choosing one kind takes the other off), and **Cancel** puts the saved worker back. In the start step the choice is what **Start** runs.
- A choice that the lists no longer know (a lane or sub-agent that was removed) stays on the button as `name (not found)`, with its own row in the dialog marked **Not found**, and is never silently turned into Claude (default). Starting on it is refused with the reason; you can pick another worker in the same step.
- **Keyboard.** The focus moves into the dialog (to the search box) and Tab stays inside it. The arrow keys move between rows (Up from the first row goes back to the search box, Home and End jump), Enter or Space picks the row, Left and Right move between the tabs, and Esc closes the dialog and returns the focus to the button. A click outside the dialog closes it too. On a narrow screen (640 px or less) it fills the screen. It is a dialog with `aria-modal`, labelled **Choose a worker**; the card page behind it cannot be reached while it is open.

The field uses the same checks as `board_update`: an unknown or unapproved lane, an unknown sub-agent, or a milestone or thread is refused with the message shown above the buttons, and nothing else of that save is written. The field is not there on a milestone or a thread, on a new card (save it, then pick a worker), or when there is nothing to pick (no delegate skills, no sub-agents) unless the card already has a worker (so that one that is gone can be removed). It is also not on the [remote page](security.md#opening-the-board-from-your-phone-tunnel): a lane sends the card's work to another company's CLI, so the tunnel cannot set, change or remove a lane or an agent (the server refuses with a message that says so). The dialog only reads the lanes and the sub-agents; it never changes the lane config.

**Start as thread, and the worker.** The step has the **Worker** field, preselected with the card's own. A card with no saved worker has the last worker Claude used on it preselected, when a thread can run as it (a listed sub-agent, or a listed and approved lane); otherwise it is **Claude (default)**. If you start with that preselection, it is saved on the card like a choice you made, and the step tells the server what it showed as usual. Choosing another worker switches the step at once: a lane brings its plan (below), a sub-agent says "Runs as sub-agent `<name>`" with its model and effort and keeps the Brief or Full copy and Mode choices, and **Claude (default)** is the usual step. **Start** saves the chosen worker on the card (or removes it) and starts the thread, in one click; if the start is then refused, the card keeps the worker you chose. The step tells the server which lane or agent it showed (`expectLane` and `expectAgent`), so a card whose worker changed meanwhile (Claude changed it, a pull did, another tab did) is not started as a worker you did not see: Start is refused with "the card's worker (lane or agent) changed since you looked at it" and the step is drawn again for the card as it is. When the step is drawn again for any reason, your session, mode and context choices are kept. A `lane` or `agent` in a card file that is not a name (a hand edit) is ignored by the page and left as it is by a save. A card file that holds both is shown, and started, with its lane. An older version (0.16.0 and before) knows only the lane: it ignores the `agent`, so if it sets a lane on a card that has an agent, both stay, and if it then removes that lane (meaning "no worker") the agent comes back as the worker. Set workers from this version when versions are mixed. Likewise a 0.16.0 start of a card with an agent ignores the card's agent; the board's page of this version names the agent in the start request, so a 0.16.0 server runs it too.

## On the board

- **Tag.** A card with a lane has a tag in its foot with a hexagon icon, the lane's name and its provider, such as `code-codex · codex`. For a task or idea whose lane is not in the loaded lanes the tag reads `name · not found`, and if it is not approved `name · not approved` (a long name is cut short, never these words); hover for a sentence about what to do. A thread's tag comes from the lane it started on, whatever the lanes are now. In `board_list` the lane follows the title, as `{lane: code-codex}`.
- **Card page.** The details list shows Lane, Provider, Model, Effort (or Variant, for a lane that has one), Access (**Read-only**, **Can edit files** or **Full access (no sandbox)**; a read-mode thread and every agy lane show Read-only) and Source (**This project** or **All projects**); a thread's page adds **Follow-up** (Possible, or why not: no session from the provider, or a lane that is no longer found, approved, on the same provider or installed, in which case the message box is off too) and shows the provider's session id. For a lane that is not found or not approved it shows the Lane row and a one-line hint. A card without a lane shows none of this.
- **Start as thread, for a card with a lane.** The step says "Runs on lane `<name>` · `<provider>`" with its model and effort, and that the lane's CLI sends the brief and the files it reads to that provider. It says which provider's session it starts, has no Full copy, and offers only Read-only when the lane is read-only or runs on agy. When the card has **Allow full access** on, it also offers **Full access** (an agy lane then offers Read-only and Full access; a read-only lane never does). If the lane is not found or not approved, the step's Start button is off and says why; you can pick another worker in the same step.
- **Known limits.** A lane on a small or low-effort model can answer without doing the work (a low-effort codex lane once replied without reading any file); the report says what the provider said and nothing more, so check it against the working tree. A provider's step map is read whether it is fenced as `thread-map`, `threadmap` or `thread_map`; a map that cannot be read is dropped from the report instead of being shown raw (for every thread, not only lane threads).
- **Known gap.** A session still running an older plugin version ignores `card.lane` in its "Start as thread" and runs the thread on Claude. An older version also refuses a follow-up on a lane thread ("has no session yet"), because the thread's own `sessionId` stays empty. When an older version deletes a lane thread's card it cannot delete the thread's log folders (`cN.tM.lane`, which hold the brief and the provider's own logs), so they stay until a session on this version next sweeps the logs: it does so when a card is removed and when the plugin's server or board starts for a project, removing only log entries of cards that no longer exist. If the plugin process is killed outright while a turn runs, the relay may keep running until it finishes or times out.
