# Security and the tunnel

Part of the thread documentation: [index](README.md).

## Security

What the plugin runs, sends and stores:

- **Runs on your machine:** a local MCP server and five hooks (at session start, on each prompt, when a turn ends, and when a sub-agent starts or stops), all plain Node scripts in this repository. The turn-end hook starts a tiny Node process after every turn, whatever the setting; it exits at once when [waking](reviews-and-waking.md#waking-the-session) is off, when the session is a headless run, or in a side thread, having read at most the project's settings. Only when waking is on and someone is at the session does it stay, watch the project's settings and state file, and write one small `waiter-<session>.json` file; it makes no network request. The two sub-agent hooks run in every session. `SubagentStart` reads the project's `state.json` and settings and, only if the project has a task or idea and is not chat-only, starts a short background Node process and returns at once (Claude Code writes the agent's `agent-<id>.meta.json` file, which holds the description, only after the start hooks have returned, so the hook cannot wait for it). That process waits up to 5 s for the meta file and, when the description starts with `[cN]` for a task or idea of the project, writes the run into `state.json`, plus the prompt file in the logs folder. `SubagentStop` always reads `state.json` to see whether the agent has a run, and reads the meta file when it has none; for a tracked agent it also reads the agent's transcript, then writes the run, the snapshot and the report file. Without a marker they write nothing and print nothing. For each thread turn it starts the `claude` CLI in the background, in your project folder, or, for a thread on a [delegation lane](delegation.md#delegation-lanes), the provider's relay script from the delegate skills, which starts that provider's CLI. To list [delegation lanes](delegation.md#delegation-lanes) it runs the `delegate-setup` skill's `config.mjs load` script with Node, without a shell and with a time limit, at most once every 30 seconds per project; the script only reads, and the plugin never writes the lane config or its approval.
- **Flags it passes to a thread:** read mode passes `--permission-mode dontAsk` and `--disallowedTools Edit Write NotebookEdit`, so a read thread stays read-only even when your own Claude Code settings skip permission prompts; write mode passes `--permission-mode acceptEdits`. Only [full access](#full-access), which the user allows per card on the board, passes `--permission-mode bypassPermissions` (and the lane flags in the section below); nothing else skips permissions. Every thread gets `--allowedTools WebSearch WebFetch` (see `THREAD_ALLOW_TOOLS`), and `--add-dir` for folders you named. It never edits your Claude Code settings.
- **Reads:** the end of the main session's transcript, to get the session's title and its model and effort; for a sub-agent run recorded on a card, that agent's transcript and meta file under `~/.claude/projects/` (or `$CLAUDE_CONFIG_DIR/projects/`) (read-only, only the file recorded on the run, never a symlink or a path from the board page); the agent files in `.claude/agents/`; the two `config.json` settings files; only when the `codeMap` setting is on, whether `graphify-out/GRAPH_REPORT.md` exists in the project and its modification time, compared with the last commit from `git log -1` (run without a shell and with a time limit), to decide if a thread's first prompt gets the [code map](threads.md#code-maps-graphify) note (the map itself is never read); and the output of the delegate script (lane names, providers, models, efforts and whether a project's lane config is approved).
- **A lane run sends your work to another company.** A thread on a lane runs `codex` (OpenAI), `agy` (Google Antigravity), `opencode` (whatever provider its model uses) or a separate `claude` session, through the delegate skills' relay. That CLI sends the brief, your task and whatever files it reads to its own provider, under that provider's terms; the plugin does not control or see this. A write-mode lane lets that provider's CLI edit files in your project and, for `codex` and `claude` lanes, run shell commands there, under that CLI's own sandbox and permission rules and not Claude Code's; a write-mode `opencode` run approves its own actions without asking, and a codex lane whose sandbox is `danger-full-access` has no sandbox at all. The board can start such a run: **Start as thread** on a card that has a lane runs on that lane, in write mode if you choose it in the start step (the lane is the card's: the start step saves a lane you choose there on the card first, and the tunnel cannot set one). Use read mode for a lane unless you want edits, and do not give a lane to a card whose note should not leave your machine.
- **The board makes no network calls; the plugin makes two optional ones, the update check and the tunnel; Claude and the lanes still talk to their providers.** The plugin's own code (the MCP server, the hooks and the board) makes no network requests and has no telemetry, except the [update check](#the-update-check) and [the tunnel](#opening-the-board-from-your-phone-tunnel), both off until you ask. Its only listener is the board on `127.0.0.1`, and the board page loads nothing from the internet (the "Updated" and "is out" notes on the board are drawn from what the local server reads from disk). The tunnel, which you start yourself with `/thread:board --tunnel`: it runs `cloudflared`, which connects to Cloudflare, and a second listener on `127.0.0.1` that only that tunnel reaches. Claude Code sessions, the main session and every thread included, send their context to Anthropic as any session does, and a thread can search and fetch the web; a lane sends its brief and files to its own provider (see the lane point above). Installing the plugin does not change that.
- **Stores,** all in the data directory on your machine:
  - each project's cards, thread replies and logs (`projects/<key>/state.json` and `logs/`), including each card's sub-agent runs (a preview of the prompt and report, tokens, the path of the agent's transcript), its history, and, in the logs folder, each run's full prompt, full report and a snapshot of its steps;
  - each card's [waiting items](reviews-and-waking.md#waiting-for-you) and your answers to them, in the same state file (for a project [kept in the repo](storage-and-sync.md#keeping-the-board-in-your-repo-claudethread) they are in the card's file in the repo instead, and anyone with the repository can read them, since repo files are not owner-only; only which session asked stays here, in `projects/<key>/repo.json`);
  - `projects/<key>/milestone-layout.json`: the cell of each milestone you moved on the [Milestones map](board.md#the-milestones-view), never put in the repo;
  - the settings files, `config.json` (global) and `projects/<key>/config.json`, if you ran `/thread:setup`;
  - `setup-hint`, an empty marker file that records that the setup hint was shown;
  - `seen-version.json`, the plugin version this machine last announced as updated, and `update-check.json` (only with [the update check](#the-update-check) on), when GitHub was last asked and the latest release version it named: nothing else from the answer is kept;
  - `board.token`, the board's access token;
  - `board-link.txt`, the board link with that token in it, written by `board_open` for you to open by hand (owner-only, like `board.token`);
  - `tunnel-link.txt`, only while a tunnel is open: the remote link with the tunnel's token, for you to open on another device (owner-only; removed whenever the tunnel ends: `--tunnel stop`, `--stop`, the 12 hours running out, `cloudflared` dying, or the session that owns it closing; one left by a session that was killed outright is removed when the next tunnel starts, and the board's **Phone link** item never reads the file, so it shows nothing for a tunnel that is not running);
  - `board.stopped`, a marker that exists while the board is stopped with `/thread:board --stop`;
  - `tunnel.pid`, only while a [tunnel](#opening-the-board-from-your-phone-tunnel) is open: the process ids of its watchdog, its `cloudflared` and the session that owns them, so a leftover one can be ended. The tunnel's token is written to disk only in `tunnel-link.txt`, while the tunnel is open;
  - `projects/<key>/waiter-<session>.json`, one small file per session while [waking](reviews-and-waking.md#waking-the-session) is on: the background waiter's id, the answers that already woke the session, when it last woke the session and when a turn last started. Files not touched for a week are removed.

- **Web access is pre-approved for threads, with no prompt per site.** A full thread holds your whole conversation, and any thread can read the project, so a malicious page could try to talk it into sending that content somewhere. If that matters for your project, set `THREAD_ALLOW_TOOLS=none`.
- **The board is local, unless you turn on the tunnel.** It listens on `127.0.0.1` only, checks the request's host and origin, and requires the access token. `/thread:board` opens your browser with a one-time code (a random 128-bit value that works once, for 2 minutes, and is held in memory by the process that serves the board): the page trades it for the token with one request that checks the board's own origin and is rate-limited, and the tunnel never reaches it. The token itself is never on a command line, where any process of yours could read it. The answer Claude gets holds only the address, and the page keeps the token in your browser's local storage so the address works in later tabs. Stopping the board (`--stop`) replaces `board.token`, so a token a browser kept (and that a process that later takes the same port could read from the page) opens nothing; moving to another port without stopping does not replace it. With `/thread:board --tunnel` a second listener, also on `127.0.0.1`, is reached through a Cloudflare tunnel; it has its own short-lived token, a fixed list of allowed routes and limits, and is described in [Opening the board from your phone](#opening-the-board-from-your-phone-tunnel). The token is stored in `board.token` in the data directory, readable only by you, and the full link in `board-link.txt` next to it. **Claude is not shown the board token or the tunnel's token in a tool result**: `board_open` opens the browser itself and answers with the tokenless address, `open: false` only returns the address, the chat links to waiting items are tokenless too, and the remote link stays out of the answer (it is in the board's **Phone link** item and in `tunnel-link.txt`). This is what keeps Claude from calling the board's API as you (for example to approve its own review item and pass the done gate). It is not a sandbox: an agent with shell access can still read `board.token`, `board-link.txt` and `tunnel-link.txt` from the data directory, so the gate guards the normal path. The confirmation codes (for the tunnel, for waking, for a report or end from another session) do go to Claude in the tool's reply: they make Claude ask you, and nothing checks that you agreed. The board page cannot change the settings. Its only writes besides cards and threads are your answers to [waiting items](reviews-and-waking.md#waiting-for-you), through `POST /api/p/<project>/cards/<card>/waits/<item>`, which passes the same token, host, origin and JSON checks as every write, takes only an answer for an item that is still open (the text, the chosen options, the tick or the verdict, and a comment), validates it for the item's kind and writes nothing else. They change through `/thread:setup` (Claude calls the `config_set` tool, which a side thread is not allowed to use) or by editing the files yourself.
- **Full access is a switch only you can turn on, per card, on this machine's board.** See [Full access](#full-access).
- **Read mode keeps a thread from editing files, but is not a sandbox**, as described in [How threads work](threads.md#how-threads-work): a shell command or tool that your own allow rules approve by name still runs.
- **Thread and card contents are stored unencrypted** in the data directory, including each thread's replies. On macOS and Linux the data directory and the folders in it are readable only by you (mode 0700) and the files the plugin writes are 0600: the state, settings, logs, briefs, run prompts and reports, and the board token. The plugin makes the folders owner-only when it creates them and, once each time a session starts its MCP server, narrows the ones an older version made with the default modes. It changes only what you own, follows no symlink, skips hard-linked files and touches nothing outside the data directory; when `THREAD_DATA_DIR` names a folder, only the plugin's own files and its `projects` folder in it are changed, not the folder itself. A session still on an older plugin version writes new files with the default modes until a newer session next starts, so the owner-only folder is what keeps them private in the meantime. On Windows it does nothing of this kind, and a filesystem that ignores modes (some network or FAT-style mounts) keeps whatever it gives.

## Full access

A thread can run in mode `full`: no sandbox and no permission checks, so it can use the GPU, the network, every file and any command, as you. It is for work such as rendering video on the GPU, which a sandbox blocks. Full access is what lifts the sandbox for the lanes that have one and for Claude threads: an `opencode` lane in write mode (it approves its own actions with `--auto` and has no sandbox) and a `codex` lane whose sandbox is already `danger-full-access` run without a sandbox in write mode, with no switch needed. What the plugin passes: a Claude thread gets `--permission-mode bypassPermissions` instead of `acceptEdits`; a [delegation lane](delegation.md#full-access-on-a-lane) thread gets `--sandbox danger-full-access` (codex) or `--dangerously-skip-permissions` (claude, agy); an opencode lane gets what it gets in write mode, since it has no sandbox. The plugin does not change Claude Code's own settings, so a sandbox or deny rule you configured in your own settings is outside what it passes.

- **Who can allow it.** Only you, on the board on this computer, with the **Allow full access** switch on a task or idea's page ([Full access](board.md#full-access)). Claude's tools cannot: `board_add` and `board_update` refuse a call that names it, and `thread_start` with mode `full` is refused unless it names a card that has the switch on, with a message that says you can allow it on the card's page. A milestone has no switch. The phone link (the tunnel) cannot turn the switch on or take it away: the route refuses a save that carries it, and the tunnel can start no thread.
- **It stays on this machine, and it is for the card's text.** The switch is kept in this machine's own record and never in a card file of a project [kept in the repo](storage-and-sync.md#keeping-the-board-in-your-repo-claudethread); a card file that says it is read as if it did not, so a pull cannot give your machine full access. With the switch the board keeps, also only here, a fingerprint of the card's title and note: when they change after you allowed it (a collaborator's push, or Claude editing the note) the switch counts as off until you allow it again on the card's page, so text that was added afterwards cannot ride on your yes. An edit you make yourself keeps it. A card that was started as a thread is allowed by its own switch alone (its task was fixed at the start), and a thread that works for another card is allowed only by that card, which must be a task or idea, never another thread. When a repo card becomes a thread, the thread carries the switch and the card's own record drops it, so a switch you took away from the thread does not come back with the card if the thread is removed.
- **When it is checked.** At `thread_start`, at the board's **Start as thread**, at every follow-up (`thread_continue`, the board's message box) and again when the runner launches a turn (for a card that is not kept in the repo; for one that is, the start and the follow-up check). The runner's own check does not see a card that is a file in the repo (it reads this machine's local store), so there only the start and the follow-up check; a card that is simply missing fails the turn. Taking the switch away stops the next turn, and the board's thread page has a **Take away full access** button for it; a turn that is already running is not stopped (end the thread for that).
- **The limit, as with the done gate.** This is not a sandbox against an agent that has a shell: the same caveat as [the board's token](#security) applies. An agent that can read `board.token` from the data directory can call the board's API as you, including the call that turns the switch on. The switch guards the normal path, so a session cannot start a full-access thread by accident or on its own say-so; it does not stop a process that is already running as you with shell access and is willing to read your token.
- **A thread in this mode is shown as such.** The board shows **Full access** on the card and on the thread's page, and `thread_status` says it.
- **An older plugin version** that reads a thread whose mode is `full` runs it read-only: it knows only `read` and `write`, and anything else is read mode there. In a project that is not kept in the repo an older version keeps the card's switch on its fields without using it. In a project kept in the repo, an older version (0.24.1 and before) rebuilds a card's local record from the fields it knows on any write to the card, so the switch is lost and has to be set again; that is safe, since nothing starts full access without it (tested).

## The update check

Off by default. With the `updateCheck` setting on (`/thread:setup`, or `config_set` with your yes), the plugin's MCP server asks GitHub which release of thread is the latest, so the session note and the board can say when a newer one is out. It is the only network call thread makes besides the optional [tunnel](#opening-the-board-from-your-phone-tunnel); the board page itself still makes none.

- **What it sends:** one plain `GET` to `api.github.com/repos/ahmed0thman/thread/releases/latest`, with a `User-Agent` of `thread-plugin/<your plugin version>` (GitHub requires one) and `Accept: application/vnd.github+json`. No data about you, your projects, your cards or your machine, and no token or cookie. GitHub sees the computer's network address, as with any request.
- **What it keeps:** only the release's version (its `tag_name`) and the time of the request, in `update-check.json` in the data directory. Nothing else of the answer is read or stored.
- **When:** at most once every 24 hours per machine, in the background when the MCP server starts, with a 5-second limit and no retry. A failure is silent (a line on the plugin's stderr log) and does not block the server or any tool call; the attempt still counts for the 24 hours. Never in a side thread.
- **Who can turn it on:** you. `config_set` answers `CONFIRMATION REQUIRED` and saves nothing until you have agreed, as for waking; a side thread cannot change settings. The setting is this machine's own: for a project kept in the repo it is stored in the data directory, never in the repo's `config.json`, and a committed file cannot turn it on.
- **Without it,** nothing tells you a release exists unless you turn on Claude Code's [auto-update](configuration.md#staying-up-to-date).

## Opening the board from your phone (tunnel)

`/thread:board --tunnel` opens the board to the internet for 12 hours, through a [Cloudflare quick tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/do-more-with-tunnels/trycloudflare/), so you can look at it from your phone while you are away from your desk. It is off unless you ask for it.

**Set up (once).** Install `cloudflared`, Cloudflare's tunnel program. You need no Cloudflare account, and the plugin never downloads anything itself.

| System | Install |
|---|---|
| macOS | `brew install cloudflared` |
| Windows | `winget install --id Cloudflare.cloudflared` |
| Linux | Cloudflare's package repository, or the direct download from [developers.cloudflare.com/tunnel/downloads](https://developers.cloudflare.com/tunnel/downloads/). A plain `apt install cloudflared` does not work on every system. |

The plugin finds `cloudflared` on your `PATH`, or in the usual install places (`/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`, and `%ProgramFiles%\cloudflared` on Windows). When it is missing, `--tunnel` tells you the line for your system; run the command again afterwards.

**Use.**

- `/thread:board --tunnel` asks you first (see below), then starts the tunnel and opens a remote link and says the time it stops working and what the link allows. The link is not in Claude's answer: copy it from the **Phone link** item in the top bar of the board on this computer, or from `tunnel-link.txt` in the data directory. It looks like `https://<words>.trycloudflare.com/#t=<token>/<project>`. Open it on your phone.
- Run it again to see the same link and expiry. Asking again does not extend it.
- `/thread:board --tunnel stop` closes it at once. `/thread:board --stop` closes it too, as does anything that ends the board: closing the Claude Code window that serves it, or a newer plugin version taking the board over. A takeover does not carry the tunnel over; run `--tunnel` again.
- The tunnel runs from the session that serves the board. From another session, `--tunnel` asks that session to start it, so it works from any window. If the board is served by a session on an older plugin version, `--tunnel` says so: run `/thread:board` in an updated session first (it takes the board over), then `--tunnel`.

The page shows a **Remote** badge in its header with the time the link stops working. The cards, the Waiting view and the thread pages work as they do at your desk, and the page polls for changes as usual.

**What the link allows.** Whoever has the link acts as you on this board, from anywhere on the internet.

- **It can read:** every project on the board with its absolute path (which contains your username), every thread's reports and transcripts, sub-agent run prompts, reports and steps, the session list, the agents list and the lane settings.
- **It can do:** create and edit cards (which gives Claude new instructions, like a card you add yourself), answer or close [waiting items](reviews-and-waking.md#waiting-for-you), alone or all the drafts together (which can approve a review, and wake Claude when [waking](reviews-and-waking.md#waking-the-session) is on, which may then change code), [notify Claude](board.md#notify-claude) about a card it has not seen (its title and note reach Claude as if you had typed them, whether or not waking is on; with waking on that also wakes it), press **Confirm approval** on a card in a project [kept in the repo](storage-and-sync.md#keeping-the-board-in-your-repo-claudethread) whose approval came from another device (which makes this machine count it for the done gate), and ask for a thread's report to go to the main session (or take the request back). It acts as you, so it can also move a card that has criteria to done, or edit those criteria, as you can on the local board.
- **It cannot:** start a thread from a card, message a thread, end a thread, delete a card, mark a run as stopped, forget a project, stop the board, or change settings. These are refused with "not allowed through the tunnel", and the page hides those controls. It also cannot turn a card's **Allow full access** switch on or off (a save that carries it is refused whole, and the page shows the switch disabled), and it cannot set, change or remove a card's lane or sub-agent (a lane sends the card's work to another coding CLI, and an agent decides who works on it when it starts): a card save that carries either is refused whole, with a message that says so, and the page hides the Worker field. It can still read the lane and agent lists. The rest of a card, even one that has a lane, can be edited. It cannot change the Milestones map's layout, links or names either. The update notes of the board (`/api/update`) are not on the tunnel's allowlist either, so the remote page shows none. The server enforces this; hiding the controls is only for convenience.

**Treat the link like a password.** Do not paste it into chats or issue trackers, and close the tunnel with `--tunnel stop` when you are done. The link carries its token after a `#`, which a browser never sends to a server, so Cloudflare does not see it in the address; it does carry all the traffic of the page, because Cloudflare is the path between your phone and your computer. The page keeps the token in that browser's local storage (for that tunnel address only) so a reload works; it is useless once the tunnel closes or expires. The link is kept out of Claude's tool answers because its token can answer waiting items (and so approve a review): it goes only to the board page on this computer (over the board's own token) and to the owner-only `tunnel-link.txt`.

**Opening it needs your yes.** Claude does not open the tunnel on the first call: `board_open` answers "CONFIRMATION REQUIRED" with a code and opens nothing, Claude tells you what the link allows (the lists above), and it calls again with the code only after you agree. The code works once and expires after 10 minutes. Showing a link that is already open, and closing it, need no code. A side thread cannot open or close the tunnel at all.

**What it needs.**

- The computer awake, and the Claude Code session that serves the board still open. If the computer sleeps or goes offline, the link does not load until it is back (the 12 hours still run out on the clock). If the session closes, the tunnel is closed with it.
- Outbound access from the computer to Cloudflare on port 7844 (QUIC over UDP, or HTTP/2 over TCP). A work network or a firewall may block it.
- No uptime guarantee. A quick tunnel is a free service meant for tests; it can drop, and its address changes every time.

**How it is kept safe.** Everything below is the same on every system.

- The tunnel never points at the board's normal port. The plugin opens a second listener, on `127.0.0.1` and a free port of its own, which only the tunnel reaches.
- That listener accepts only a fresh random token made for this tunnel (at least 32 bytes, new each time the tunnel starts, compared in constant time). It never accepts your `board.token`, and the normal listener never accepts the tunnel's token.
- It requires the tunnel's own host name in the `Host` header, requires every write to come from exactly `https://<that host>`, and believes no `X-Forwarded-*` header.
- It answers at most 32 requests at once (then 503) and 60 changes a minute (then 429).
- The 12 hours are checked on every request, by a timer, and once a minute against the clock (a timer stands still while a computer sleeps); a late request gets "the tunnel has expired". At the end, or on `--tunnel stop`, the plugin revokes the token, closes the listener and stops `cloudflared`. It also stops `cloudflared` when its own process ends. A board that has been closed starts no new tunnel.
- `cloudflared` runs under a small watchdog (`scripts/tunnel-watchdog.mjs`) that ends it when the session that owns it ends, even if that session is killed outright, and at the expiry. After a hard kill, `cloudflared` is gone within a few seconds. The plugin records the watchdog, `cloudflared` and the owning session in `tunnel.pid` in the data directory. If a record is left whose owning session is gone, the next time the board starts or a tunnel is opened the plugin ends what it names, but only a process that is still `cloudflared` started with this plugin's arguments. It never touches the tunnel of a session that is still running.
- Responses carry `Referrer-Policy: no-referrer` and `Cache-Control: no-store`.
